**Library signatures (server, `ledger-sweep-batch.ts`):** `evaluateSweepBatch(exec, input, ctx: { actorUserId; callerCanManage; now; lock: boolean })` (the one evaluator: `lock = false` for preview on `db`, `true` inside the create transaction, which locks the **source rows alone** `ORDER BY id FOR UPDATE`, then reads categories, mirror targets, closeouts, live copies, sent acknowledgments, matches and filings in follow-up selects, never an outer join under `FOR UPDATE`); `createSweepBatch(input, actor)`; `voidSweepBatch(legId, actor, reason)` (locks leg and copies with `lockDecisionGroup(tx, legId, "update")`); `listSweepCandidates(exec, { now, cap = 500 })` returning `{ eligible, heldBack: { row, refusal }[], inPendingBatch }`; `markSweepCloseouts` / `unmarkSweepCloseouts`. Also `listMatchedTransactionIds(exec, ids)` added beside `getMatchForTransaction` in `reconciliation-queries.ts` (used by void and by `not_matched_to_deposit`).

**Create, in order, one `db.transaction`:** resolve funds and call `checkTransferDirection()`; validate both bank accounts with `validateBankAccountForEntity(…, { requireActive: true })` (source on the Club entity, destination on the Foundation); lock and evaluate; refuse (`rows_claimed`, `rows_refused`, `manage_required`, `reason_required`); `total_too_large`, then `total_mismatch` (derived from the locked rows, the client total is never read); insert the leg (expense, Club activity fund, sweep date, **`category_id` per A1**, fresh `transfer_group_id`, generated memo, source bank account, `board_minute` trimmed to 500, status from `total > thresholdCents`), then the copies (one multi-row insert: income, Foundation charitable fund, destination bank account, **gift date**, the mirror target as category, amount, party, memo, `beneficiary_cause`, `payment_method`, `donor_id`, `board_minute`, `status` equal to the leg's, `recorded_by_user_id` = actor, both pointers, `transfer_group_id` NULL; **not carried:** check number, receipt key and waiver trio, `public_note`, `budget_line_id`, `dues_payment_id`, reconciliation fields); the `sweep_batch_created` note; commit. A `23505` on `ux_ledger_txn_swept_from_live` maps to 409 `rows_claimed` naming the claimed rows. After commit, a pending batch calls `notifyPendingApprovers()` (best effort, isolated, `console.error` on failure, never fails the 201).

**Void, in order:** non-UUID/absent 404; `lockDecisionGroup` `FOR UPDATE`; no copies `not_a_sweep`; then `pending_use_reject`, `already_rejected`, `approved` (`leg.approved_at`), `reconciled` (any row `reconciled` or `reconciled_session_id`), `matched` (any row in `ledger_reconciliation_matches`), `receipt_sent` (a sent acknowledgment on any copy), `prior_fiscal_year` (leg dated before the current fiscal year), `period_filed` (any copy's year filed); each names its next step in the copy record. Then: count the unsent acknowledgments, write `sweep_batch_voided` through `recordLedgerAudit` in the same transaction, delete the copies, then the leg (RESTRICT forces that order), assert row counts, roll back on a mismatch with a sentinel.

Known noise: the B-165 name-drift prompts and ten long FK names. *No CHECK constraint* ties the two pointers together (`push` support for checks is the less-trodden path); the single-writer scan test below enforces that only `createSweepBatch` ever sets them, and sets both.

## 5. Edge cases, risks and the live checks

**Decisions on the questions put to this confirmation**
- *Inactive Club category at batch time:* irrelevant. Sweepability is decided by the **mirror target** (active, Foundation, charitable, income), never by whether the Club category is active; a gift keyed before a category was retired stays sweepable.
- *Cleared or inactive mirror at batch time:* re-read under lock; the row is refused (`no_mirror`, `mirror_inactive`, `mirror_invalid`), the whole batch writes nothing, and the 409 names the row. A mirror **re-pointed** between preview and create silently changes the copy's category (and therefore its receipt flag); the server always uses the current mirror and the created response reports `byCategory` on the detail GET. Believed negligible; recorded by **S11**.
- *Zeffy payout versus the gift sum:* **no such validation exists in 2a or 2b.** The ledger holds no Zeffy payout figure until B-120; the sweep total is the sum of Public Funds rows the treasurer selected, and the typed bank amount must equal it. Gifts summing to more than the 2026-10-01 lump (V7) is **expected**, not an error: the lump covered an unknown subset, so the closeout is per row and there is no "carried through $X" arithmetic. Fees and tips that make the Zeffy payout differ from the gifts are the existing Club-side batch-match situation (B-120). The only money warnings are `exceeds_fund_balance` and `unmatched_sources`, neither blocking.
- *Statement restatement:* a copy dated in a month whose Foundation statement was sent restates its Twelve-Month and Annual columns. **Refuse only what would hide a sent statement; warn and audit what merely restates one** (DECISION-114). A batch cannot hide one (verified above), so nothing is refused on this ground; the preview returns `sentStatementMonths` with `addsCents`, the create note records the months. The helper is `findSentStatementMonth(exec, { entityId: foundation, txnDate, fundKind: 'charitable' })`, imported as is (B-196), deduplicated per month.
- *Aged funds (N4):* FIFO stays (DECISION-105). Back-dated copies add Foundation balance but no trailing-window income (the rule reads `txn_date`, `ledger-queries.ts:3197-3231`), so a large batch of old gifts can start the Foundation warning; production headroom is about $20,107 (analyst aggregate, not the app's computation). It is a warning, not a block. **S7** measures it with a positive control.
- *A re-keyed Zeffy gift already swept in a lump:* the closeout marks it; nothing else prevents it. The first production batch (the three FY2025 gifts) is `manage` tier with a typed reason by construction.

**Risks carried into Phase 4/5 (all believed, unmeasured unless a check is named)**
- `drizzle-kit push` recreating the partial unique index (S6).
- `period_filed` is only as good as the filing tracker (A9); an absent prior-year row means "not filed" (S13).
- A reconciliation of the Foundation credit by hand-picking N rows remains possible and correct; "Match this batch" is 2b.
- A pending batch holds its sources (they cannot be selected again) until approved or rejected; reject frees them with no cleanup write, leaving N rejected rows in the Foundation register (accepted, ruling 5).
- The register still offers Edit and Delete on a leg or copy until 2b; the server refuses with the sweep message. Acceptable because no UI reaches the create route until 2b ships in the same release.
