## Findings

### MEDIUM-1 — Seven admin list-pages lack per-feature gate at the page level

**Severity:** Medium  
**Locations:**
- `src/app/(dashboard)/admin/announcements/page.tsx` (no auth/feature check)
- `src/app/(dashboard)/admin/campaigns/page.tsx` (no auth/feature check)
- `src/app/(dashboard)/admin/events/page.tsx` (no auth/feature check)
- `src/app/(dashboard)/admin/groups/page.tsx` (no auth/feature check)
- `src/app/(dashboard)/admin/members/page.tsx` (no auth/feature check)
- `src/app/(dashboard)/admin/roles/page.tsx` (no auth/feature check)
- `src/app/(dashboard)/admin/users/page.tsx` (no auth/feature check)
- `src/app/(dashboard)/admin/testimonials/page.tsx` (no auth/feature check)
- `src/app/(dashboard)/admin/permissions/page.tsx` (no auth/feature check)

**What's wrong:** These pages query the database directly without calling `auth()` or `hasFeature()`. They rely entirely on `src/app/(dashboard)/admin/layout.tsx`, which only checks that the user has `FEATURES.ADMIN_DASHBOARD` (or `session.user.role === "admin"`). A logged-in member who is granted the `admin.dashboard` feature — but not, say, `members.edit` or `admin.users` — can navigate directly to `/admin/members` or `/admin/users` and see the data.

By contrast, other pages in the same directory (`contact/page.tsx`, `suggestions/page.tsx`, `membership/page.tsx`, `programs/page.tsx`) correctly check the precise feature for their surface.

**Why it matters:** This is a defense-in-depth gap. The API routes that back these pages do correctly gate on the right `FEATURES.*` key, so a user without `members.edit` cannot _modify_ data. But they can _read_ the full member list, user list, role configuration, and permissions matrix — data that should be restricted to the appropriate admin role. The proxy middleware (`src/proxy.ts`) would also protect `/admin/members` — but see MEDIUM-2 below.

**Suggested fix:** Each list page should call `auth()`, check the relevant feature, and redirect to `/admin` or `/access-pending` on failure. Follow the pattern already used in `src/app/(dashboard)/admin/contact/page.tsx`:
```ts
const session = await auth();
if (!session?.user?.id) redirect("/signin");
const canManage = await hasFeature(session.user.id, FEATURES.MEMBERS_VIEW);
if (!canManage) redirect("/admin");
```

### MEDIUM-3 — Three `/api/admin/` endpoints check only `auth()`, not a feature gate

**Severity:** Medium  
**Locations:**
- `src/app/api/admin/members/export/route.ts:54-58` — checks `session?.user` but no `FEATURES.*` key. Any authenticated user can download the full active-member roster as an Excel file.
- `src/app/api/admin/newsletter/export/route.ts:8-11` — same: checks `session?.user`, no feature gate. Any authenticated user can download the full newsletter subscriber list.
- `src/app/api/admin/zeffy-meta/route.ts:9-12` — checks `session?.user?.id`, no feature gate. Low data sensitivity (fetches public OG metadata), but the pattern is inconsistent.

**Why it matters:** The member export and newsletter export routes return personally identifiable information (names, emails, addresses, phone numbers) to any authenticated user regardless of role or feature assignment. A newly created account assigned only the default `member` role can call these endpoints.

**Suggested fix:**
- `members/export`: add `hasFeature(session.user.id, FEATURES.MEMBERS_VIEW)` (or `MEMBERS_EDIT`).
- `newsletter/export`: no explicit `FEATURES` key covers subscriber lists; either reuse `MEMBERS_VIEW` or add a dedicated feature key. A `REPORTS_EXPORT` feature already exists in the catalog.
- `zeffy-meta`: the sensitivity is low (public metadata only), but consistency suggests adding `FEATURES.CAMPAIGNS_MANAGE` to match the upload endpoint that uses the same feature.

### LOW-1 — `"Admin"` (capital A) in role-string comparisons never matches

**Severity:** Low  
**Locations:**
- `src/app/(dashboard)/admin/layout.tsx:25` — `userRoles.includes("Admin")`
- `src/proxy.ts:46` — `userRoles.includes("Admin")`

**What's wrong:** The database seeds the admin role as `'admin'` (lowercase), and `src/lib/auth/index.ts:181` stores role names verbatim from the DB into the JWT (`token.roles = roleNames`). Therefore `session.user.roles` contains `["admin"]`, not `["Admin"]`. The `"Admin"` half of both guards is dead; the adjacent `session.user.role === "admin"` check is what actually grants admin bypass.

**Why it matters:** The dead branch is currently harmless because the `session.user.role === "admin"` fallback always fires first for admins. But the mismatch is a latent confuser: a future developer reading the condition might assume one of the two checks is a safety net for the other.

**Suggested fix:** Remove `userRoles.includes("Admin")` from both locations, or change it to `userRoles.includes("admin")` to match actual DB values.

### LOW-2 — Two export routes check `session?.user` instead of `session?.user?.id`

**Severity:** Low  
**Locations:**
- `src/app/api/admin/members/export/route.ts:56`
- `src/app/api/admin/newsletter/export/route.ts:10`
- `src/app/(dashboard)/admin/release-notes/page.tsx:11`
- `src/app/(dashboard)/admin/subscriptions/page.tsx:10`

**What's wrong:** These four handlers check `if (!session?.user)` rather than `if (!session?.user?.id)`. The `user` object can in theory be present in the session type without an `id` (e.g., during an OAuth callback race). All other admin route handlers in this codebase guard on `session?.user?.id`, which is consistent and correct.

**Why it matters:** This is a defensive-coding inconsistency rather than an exploitable gap. Aligning to `session?.user?.id` makes the codebase uniform and removes an unlikely-but-possible edge case where a user object without an `id` slips through.

**Suggested fix:** Change all four checks to `if (!session?.user?.id)`.

**Severity:** Low  
**Location:** `src/app/api/admin/email-queue/retry/route.ts:47`

**What's wrong:**
```ts
console.log(`[Email Queue Retry] Dev mode — marking ${item.id} sent`);
```

This branch fires only when `RESEND_API_KEY` is absent (dev mode). On production Vercel it is never reached. The companion `console.log` in `src/lib/email.ts:43` has the same dev-only guard. These are the only two `console.log` calls in the codebase; all others are `console.error` in error-handling branches, which is acceptable.

**Why it matters:** Neither fires in production, so there is no functional concern. Noted for completeness because CLAUDE.md forbids `console.log` in production paths; both are strictly dev-mode branches gated on the absence of an env var.

**Suggested fix:** Either remove the logs or demote to `console.debug`. Not urgent.
