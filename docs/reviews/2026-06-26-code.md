## MEDIUM Severity

### MEDIUM-1: `get990Prep` uses opening balances only for assets estimate — produces a stale/wrong 990 determination

**File:** `src/lib/ledger-queries.ts`, lines 1517–1519

**Issue:** `get990Prep` computes `entityBalance` for the `determine990` `assetsCents` parameter by summing `fund.openingBalanceCents` — the opening balance only, ignoring all YTD transactions:

```typescript
const entityBalance = funds.reduce((s, f) => s + f.openingBalanceCents, 0);
```

Every other call site that feeds `assetsCents` into `determine990` uses the ending balance (opening + income − expenses). This inconsistency means the 990-prep worksheet can recommend a different form than the overview and the reports page for the same entity and fiscal year. For a club with significant YTD activity this could flip between 990-N and 990-EZ.

**Recommendation:** Replace with a call to `getFunds` + a pass over YTD posted transactions (reuse the transaction batch already fetched in `get990Prep`, or call `getOverview` for the entity balance). The simplest targeted fix: derive ending balance by summing the per-fund reports already computed in the same query path. Alternatively, the `get990Prep` function already fetches `funds` — add a FY transaction pass to compute the actual ending balance.

**Impact:** Low probability of triggering a real flip (most small nonprofits are well under thresholds) but it is a correctness defect in a financial feature.

### MEDIUM-2: `getComplianceOverview` duplicates the inc3 guardrail flag logic from `guardrails()`

**File:** `src/lib/ledger-queries.ts`, lines 1132–1162

**Issue:** The IRS revocation check (3 consecutive unfiled returns) and the overdue-filings check are each evaluated twice:
1. Once inside `guardrails()` in `src/lib/ledger.ts` (the canonical check), which is called by `getOverview`, but `getOverview` passes `irsFilingHistory: [], overdueFilingCount: 0` so those two checks never fire there.
2. Again manually in `getComplianceOverview` by re-implementing the same if/push logic (lines 1132–1162), then appending the results to the flags from `getOverview`.

The result is correct only because the `getOverview` path always passes empty/zero values. But the duplication means the flag text, severity, and `policyCite` strings exist in two places: `ledger.ts` (the source of truth) and `ledger-queries.ts`. Any change to the wording of the flag in `guardrails()` must also be replicated manually in `getComplianceOverview`, or the compliance page will show a different message than the overview.

**Recommendation:** Refactor `getComplianceOverview` to call `guardrails()` once with all inputs (inc1 + inc2 + inc3), discarding the `getOverview` guardrail result for the compliance page. The inc1/inc2 guardrail inputs would need to be derived in `getComplianceOverview` itself, or extracted into a shared helper. This collapses the duplication to the single canonical implementation in `guardrails()`. Document the refactor as a follow-up to the first increment where the inc1/inc2 inputs were split from inc3.

### MEDIUM-3: Impact page visibility logic silently bypasses the `philanthropyVisibility` setting for non-linked users

**File:** `src/app/members/impact/page.tsx`, lines 35–45

**Issue:** The visibility check is gated on `memberId` being non-null:

```typescript
let canView = false;
if (memberId) {
  const [settings, featureEnabled] = await Promise.all([
    getSettings(),
    hasFeature(session.user.id, FEATURES.IMPACT_VIEW),
  ]);
  canView = featureEnabled;
  if (settings.philanthropyVisibility === "board" && !canView) {
    redirect("/access-pending");
  }
}
```

When `memberId` is null, neither `getSettings` nor the permission check runs. The page renders the "Account Not Linked" empty state — no data leak there. However, the `ImpactDashboard` subcomponent is only rendered on the `else` branch (when `memberId` is set), and it unconditionally calls `getPhilanthropy()`. The check for `philanthropyVisibility === "board"` correctly blocks unlinked users from the page content via redirect.

More subtle: when `philanthropyVisibility` is `"all"` (the open setting) and `memberId` is set, any member — even one without `IMPACT_VIEW` — can view the dashboard. This is the intended design per the Phase 3 spec (visibility `"all"` means all members). The code is correct. However, the `canView` variable is computed but then never used after the redirect guard — it has no effect on rendering when visibility is `"all"`. This is dead code / misleading.

**Recommendation:** Remove the `canView` variable entirely in the `"all"` code path, or add a comment explaining that `canView` is only meaningful when `philanthropyVisibility === "board"`. If the intent is that `canView` should restrict rendering even in `"all"` mode, the conditional must be updated. As written, the `canView` computation on lines 35–44 is vestigial for the `"all"` case.

## LOW Severity

### LOW-1: N+1 query in admin reimbursements page (negligible at current scale, flag for when entity count grows)

**File:** `src/app/(dashboard)/admin/ledger/reimbursements/page.tsx`, lines 84–88

```typescript
const entities = await getEntities();
let allFunds: LedgerFund[] = [];
for (const entity of entities) {
  const entityFunds = await getFunds(entity.id);
  allFunds = allFunds.concat(entityFunds);
}
```

This is a sequential await loop — one DB round-trip per entity. At 2 entities it is fine. If the entity count ever grows beyond ~5, this should be replaced with a single `SELECT * FROM ledger_funds WHERE is_active = true ORDER BY entity_id, name` query (no entity filter). The existing `getFunds(entityId)` helper is not suited for this; a new `getAllActiveFunds()` helper would be cleaner.

**Recommendation:** Document the N+1 with an inline comment noting the entity-count threshold at which to fix it. No change required now.

### LOW-2: Four tab-count queries on admin reimbursements page are sequential `listReimbursementsForAdmin` calls with `limit: 1`

**File:** `src/app/(dashboard)/admin/ledger/reimbursements/page.tsx`, lines 93–98

```typescript
const [submittedResult, approvedResult, rejectedResult, paidResult] = await Promise.all([
  listReimbursementsForAdmin({ status: "submitted", limit: 1 }),
  listReimbursementsForAdmin({ status: "approved", limit: 1 }),
  listReimbursementsForAdmin({ status: "rejected", limit: 1 }),
  listReimbursementsForAdmin({ status: "paid", limit: 1 }),
]);
```

These run in parallel (Promise.all), which is correct. However, each call executes two SQL queries: a `COUNT(*)` and a `SELECT ... LIMIT 1`. Four parallel 2-query pairs = 8 total round-trips just for tab badge counts. A single `SELECT status, COUNT(*) FROM ledger_reimbursements GROUP BY status` query would replace all 8. The existing code is correct and the overhead is small at current volumes, but it is worth noting as a complexity smell.

**Recommendation:** Add a `getReimbursementCountsByStatus()` helper in `ledger-queries.ts` that returns a `Record<string, number>`. Low priority.

### LOW-3: `guardrails()` check numbering in comments does not match the policy section numbers

**File:** `src/lib/ledger.ts`, lines 375–511

The inline comments use section-number labels that are inconsistent: the negative-balance check is labelled "Check 6" but other checks are unlabelled or use a different scheme. This creates confusion when cross-referencing the Lions Financial Transparency Policy. The check numbering appears to be historical artifact from incremental development.

**Recommendation:** Either (a) remove the numeric labels and rely solely on the `policyCite` field, or (b) add consistent `policyCite` values to all flags and drop the comment-level numbers. No functional issue.

### LOW-4: `listTransactionsForExport` does not filter by `fundId` — it includes all funds for the entity

**File:** `src/lib/ledger-queries.ts`, lines 1561–1618

This is intentional and documented: the export is entity-scoped for the full audit. However, the function signature (`entityId: string, fiscalYear: number`) gives no indication that all funds are included. A fund-scoped export from the fund detail page would silently return all funds. There is currently no fund-scoped export path, so this is not a defect — but if a fund-scoped CSV download is ever added, it would need a new helper.

**Recommendation:** Add a `fundId?: string` optional parameter to `listTransactionsForExport` and pass it to the WHERE clause, to future-proof the export interface. Document in the function comment that the current callers use entity-scope only.

### LOW-5: `csvCell` and `csvCellSafe` are both defined — `csvCell` in the export route lacks the injection guard

**File:** `src/app/api/admin/ledger/export/route.ts`, lines 21–27

A local `csvCell` function is defined in the export route without the formula-injection tab-prefix guard. The columns that use `csvCell` (Date, Fund Name, Flow, Status, Reconciled, Amount, Payment Method) are all non-user-supplied values and therefore not injection targets — this is the correct choice. However, having two similarly named functions in the same file with different safety properties is a readability hazard. A future developer adding a new column may reach for `csvCell` instead of `csvCellSafe` for a user-supplied field.

**Recommendation:** Rename the local function to `csvCellFixed` or `csvCellEnum` to signal that it is only for controlled values. Add a comment to `csvCellSafe` at the import site noting which columns require it.

## What is Healthy

- **Auth gates are complete on every ledger page and route.** All 10 admin ledger pages perform `auth()` + `hasAnyFeature()` or `hasFeature()` before any DB access. All `api/admin/ledger/**` and `api/members/reimbursements/**` routes check session + feature at the top of the handler.
- **Self-approval guards are correctly enforced in both code paths.** The transaction approve handler (`api/admin/ledger/transactions/[id]/approve/route.ts`) blocks `session.user.id === txn.recordedByUserId`. The reimbursement approve/reject handler blocks `session.user.memberId === reimb.submittedByMemberId`. Both are enforced server-side in the route handler, not merely in the UI.
- **Two-fund firewall invariant is correctly applied.** `getOverview` counts `transferGroupId` groups where the fund pair includes both `activity` and `administrative` kind. The `isGiving` helper in `ledger.ts` and the SQL predicate in `getPhilanthropy` are in sync per DECISION-024. Administrative fund rows are excluded from the philanthropy totals in both the TypeScript helper and the SQL query.
- **Receipt proxy returns 404 (not 403) for non-owned rows.** The member receipt proxy (`api/members/reimbursements/[id]/receipt/route.ts`) correctly uses 404 to prevent existence leaking when a member requests a receipt for another member's reimbursement.
- **No native browser dialogs.** All destructive actions use `<ConfirmDialog>` — confirmed by grep and inline code comments referencing the pattern explicitly.
- **No `console.log` in production paths.** All error paths use `console.error`. No `console.log` found in any ledger component, lib, or route.
- **Cents-integer money invariant is correctly maintained.** Every route handler validates `amountCents` as a positive integer. The `INT4_MAX` guard prevents silent PostgreSQL overflow. Dollar display is always `(cents / 100).toFixed(2)` — never floating-point arithmetic on the stored values.
- **Status is derived server-side.** The `POST /api/admin/ledger/transactions` handler ignores any client-supplied `status` field and derives pending/posted from `disbApprovalThresholdCents` + flow. This is documented explicitly in the code and was a Phase 3 adversarial-pass requirement.
- **Double-pay atomicity.** The `pay` action in the reimbursement PATCH handler uses a DB transaction with `WHERE status='approved'` on the update `.returning()` to guard against concurrent payment requests. The `DOUBLE_PAY` error path is handled correctly.
- **N+1 queries are absent from the critical paths.** `getOverview`, `getFundReport`, `getEntityReport`, and `getPhilanthropy` all make at most 3 sequential DB round-trips regardless of fund count, with TypeScript-side aggregation. The `listTransactionsForExport` is single-query.
- **CSV injection escaping is applied to all user-supplied free-text columns** in the ledger export (Category, Party/Payee, Memo, 990 Line Group). Controlled-value columns correctly use the simpler `csvCell` without the tab-prefix guard.
- **`isGiving` cross-reference is maintained (DECISION-024).** Both definitions (TypeScript helper and SQL predicate in `getPhilanthropy`) use the same three fund kinds and the same transfer-exclusion rule.
