# Retrospective — 2026-09-25

**One-line outcome:** Acceleration is a contributing cause for two of today's four QA-caught defects (a privacy leak that rode a self-declared Phase-1 skip, and an interrupted agent that left a money/PII-adjacent feature with *zero* Phase 1–4 record) — but the flagship defect class (six same-shaped "reported sent, wasn't sent" bugs, DECISION-102) was first caught inside a **Full**-pipeline feature's Phase 5, which means more ceremony would not have prevented it; only QA's Phase-5 rigor did. The cadence mechanism, by contrast, shows real improvement: this cycle is 15 days overdue (2.1x), not the 75–90 days of the prior two gaps — worth noting precisely, since the task brief describing this review's own trigger overstated the gap by roughly 6x.

## 2. Findings, Ranked

### 2.1 HIGH — The flagship defect class was caught by Full-pipeline QA rigor, not by pipeline ceremony, which bears directly on the acceleration question

`docs/work-log/2026-09-25-financial-report-auto-send.md` ran the complete pipeline: analyst (Phase 1) → architect (Phase 2, DECISION-100) → tech-lead (Phase 3, DECISION-101 — a genuinely substantive design pass: a partial unique index keyed on a totals fingerprint, an explicit ruling that failed sends must remain visible and resendable) → api-developer (Phase 4) → qa (Phase 5). Despite that full ceremony, the defect that became DECISION-102's defect #4 — `sendMonthlyReportToBoard()` taking `sendEmail()`'s `success: true` on a blocked non-production send at face value and permanently claiming an undelivered statement as sent — was not caught by any of Phase 1, 2, or 3. It was caught by qa in Phase 5, via an independent, unmocked reproduction of the real `sendEmail()`/`email-guard.ts` interaction (DECISION-102 itself records this: "caught in QA before ship, not after"). **This is direct evidence that the root defect shape was not a design-ceremony gap.** It was a genuine architectural blind spot — a boolean `success` field conflating "delivered," "rejected," and "deliberately not attempted" — that neither the architect's nor the tech-lead's checklist had reason to interrogate, because DECISION-085 (the deny-by-default guard) and this new durable-claim caller were each independently correct; the defect lived entirely in the *interaction* between two already-shipped, already-reviewed pieces of code.

### 2.2 HIGH — Acceleration/self-declared-skip did correlate with two of today's other three defects, in a specific and fixable way

- **`docs/work-log/2026-09-25-recurring-occurrence-visibility.md`** explicitly skipped Phase 1 as a separate agent pass ("already investigated and handed to the implementer with root cause... confirmed real during implementation"). The fix widened generateOccurrences()'s window from "upcoming only" to a ~10-year lookback specifically to restore historical rosters — and, because no independent analyst ever ran the standard five-pass review's mandated permissions pass on that change, nobody asked "who else can now see this." The result: real member names, shipped in plaintext to anonymous visitors, in a leak this very fix materially widened (a pre-existing narrower version already existed in production). qa's first Phase 5 pass **PASSED** this — it tested that a date was visible to a logged-out visitor, not that the payload was free of names. It was analyst's Phase 6 review, running an anonymous `curl` for the first time in the whole chain, that found it and returned **NEEDS REWORK**.
- **The per-message retry feature** (documented mid-file in `2026-09-25-email-silent-success.md`, under "Note on pipeline gap") has **no Phase 1–4 write-up at all** — not a self-declared skip, an outright absence. The implementing agent was interrupted before writing anything, and the code simply existed in the working tree for qa to find. qa's Phase 5 pass on it found a real, reliably-reproducible duplicate-send race (two concurrent retry clicks send the same email twice) with no preceding design record to check the fix against.

Both defects were caught — by qa in the second case, by analyst in the first after qa missed it — so the pipeline's back half (Phase 5/6) is carrying real weight here. But both are also concrete illustrations of exactly the failure modes CLAUDE.md's unapplied Edit 6 (mid-flight scope routing, now 4th cycle) and Edit 10 (background-agent verification) were written to prevent. Acceleration is not the root cause of today's most dangerous defect (§2.1), but it is *a* root cause of these two, and the existing carve-outs don't reach them.

### 2.3 MEDIUM — The Durable-Claim Exception added today is correctly scoped for its own class; two adjacent classes need a parallel carve-out

CLAUDE.md gained a "Durable-claim exception" today (Bug-Fix Variant section) making any change to a durable "this was sent" claim ineligible for a Phase 2 skip or abbreviated Phase 3, regardless of diff size, with the explicit reasoning that recognizing the trap ("am I writing a durable sent-claim?") requires no specialized knowledge — a deliberately low-bar, hard-line trigger. This is good, proportionate design: DECISION-102/103 show the class it targets (six instances in a day) and the enforcement (type-level, via `sendEmailForDurableClaim()`/`sendBulkMemberEmailForDurableClaim()`) is real, not aspirational. DECISION-102 itself is honest about the exception's limit — a brand-new caller that bypasses the new helpers and writes its own durable claim can still repeat the defect; the type only closes the gap for adopters. That's an acceptable, disclosed residual risk, not a design flaw.

What it does **not** cover, and what today's other two defects show is needed, are two structurally identical carve-outs:

1. **A public-exposure/PII exception** — modeled directly on the Durable-Claim Exception's own phrasing: any change to what data a public, unauthenticated route serves (new joins, new props crossing a Server→Client boundary, a widened query window on existing data) is never eligible for a Phase 1 skip, regardless of how small the diff looks or how "already investigated" the brief claims to be — because "am I changing what an anonymous visitor's payload contains?" requires no more specialized knowledge than "am I writing a durable sent-claim?" did.
2. **A "no silent starts" companion to "no silent skips"** — today's interrupted-agent gap isn't a phase being skipped with reasoning; it's a phase never happening at all, silently, because nobody checked. The existing rule polices *skipping* a phase without saying so. It has no equivalent for *starting implementation with no record of having entered the pipeline at all.*

### 2.4 MEDIUM — QA's methodology today was unusually strong, with one specific, fixable class of gap

Praise, specifically: the email-silent-success and retry-stranding work-logs show qa running real sabotage experiments (deliberately breaking the atomic claim three different ways to prove the fix's guarantee is load-bearing, not incidental), independently reproducing pre-fix failures via `git stash`/`git checkout --` rather than trusting the implementer's account, verifying migration idempotency by executing it twice against the dev DB rather than reading the SQL, and self-disclosing a real residual risk (the `retrying`-row stranding hazard) rather than treating a PASS as license to stop looking. `ready-to-send-badge`'s qa pass quantified a genuine performance cliff (B-71) before it became visible in production. This is exactly the standard the 2026-09-09/10 test-coverage review found missing.

The one gap: qa's Phase 5 on `recurring-occurrence-visibility` tested anonymous **page load** (does a date render) rather than anonymous **payload** (does the response body carry names) — a signed-in Playwright session structurally cannot observe what an anonymous session receives, and nothing in the checklist forced a distinct anonymous-payload check for a feature that touches member-identifying data on a public route. The work-log's own qa-process-gap note proposes exactly the right narrow fix ("curl anonymously, grep the response for a known signee name" as an explicit Phase 5 step for any `/events/[id]`-shaped change). §3 below generalizes this into a proposed qa.md edit.

### 2.5 LOW-MEDIUM — Concurrent agents sharing one working tree produced real, if contained, friction

At least three work-logs today had to spend real verification effort distinguishing "my change" from "a concurrent agent's uncommitted work in the same tree": `retry-stranding.md` explicitly notes a concurrent agent's acknowledgment-letter work was visible and had to be confirmed untouched; multiple qa passes had to reconcile a stated test-count baseline against an actual count that included another in-flight piece's tests (e.g., "task's stated baseline was 2154... the gap... is a concurrent, unrelated agent's in-progress work," and a separate pass explicitly subtracted "44 stashed financial-report tests" to match an expected number). No collision or lost work resulted — every agent's discipline of checking `git status`/`git diff` before touching anything held — but this is overhead paid on every single verification pass, not a one-time cost, across roughly ten independent work-log threads run through perhaps thirty subagent invocations in one day.

### 2.6 LOW — A near-recurrence of the PII-in-work-log pattern was caught proactively, not retroactively, this time

Three days before this session (`d15bd59`, 2026-09-22), a personal address had to be scrubbed from a committed work-log after the fact. Today's `recurring-occurrence-visibility.md` handled the identical temptation correctly and proactively: real member names surfaced during a live anonymous-curl investigation were redacted *before* the section was written into the file, with an explicit inline "PII note" citing *No Personal Data in the Repository* by name and explaining why an officer-name exception doesn't apply to signee/RSVP data. This is worth naming as a positive: the lesson from three days earlier visibly propagated into a different agent's behavior within one work week, without a new rule being written — the existing invariant's text was sufficient once one incident made the risk salient. No edit proposed here; recorded so it isn't lost.

## 3. Pipeline Efficacy — Is Today's Evidence For or Against the Six-Phase Pipeline?

**For, with a specific correction.** The full financial-report-auto-send run produced two substantive design decisions (DECISION-100/101) that a lighter pass would likely have missed — the partial-unique-index-on-`WHERE success` trick and the explicit "failure must stay visible and resendable" ruling are not things an accelerated brief would naturally arrive at. The Bug-Fix Variant, used correctly (ack-letter-blocked-claim, sendemail-unchecked-error, retry-stranding), shipped clean, well-reasoned skips with no defects. Accelerated mode, used for genuinely small, well-understood follow-on work (shared-resend-attempt, send-result-type, ready-to-send-badge), also shipped clean. The pipeline is not the problem.

**The correction:** today's evidence argues against treating "did this piece run Full/accelerated/bug-fix" as the diagnostic question at all. The better question, which the two carve-outs in §2.3 both point at, is narrower: **did this specific change cross one of a small number of named, high-consequence seams** (a durable send-claim, a public route's data payload, an interrupted handoff) **regardless of which variant the rest of the change otherwise qualifies for.** The Durable-Claim Exception already embodies this shape for one seam. The retrospective's job is to name the other seams before they produce their own six-defects-in-a-day cluster, not to relitigate whether acceleration in general should be curtailed — today's evidence doesn't support that broader claim, and narrowing the pipeline's fast paths across the board would slow down five clean accelerated/bug-fix passes to prevent two seam-crossing ones that a targeted exception handles more precisely.

## 4. Cadence Mechanism — Improved, Not Fixed

Positives, stated plainly: the actual overdue amount this cycle (15 days, 2.1x) is dramatically better than the 75–90 day gaps of the prior two cycles. Whatever combination of the 2026-09-10 retrospective's own visibility and ordinary session-start prompting is happening, it is working better than it was. Separately, and probably more importantly: **the trigger this time was not the session-start cadence check at all** — it was the analyst's own Phase 6 review noticing a cross-cutting process pattern ("two pieces today self-declared Accelerated pipelines skipping real Phase 1 analyst review") and the user acting on that observation. That is a *better* mechanism than a prose reminder competing for attention at the top of a session — it's a domain expert (the agent already reviewing the actual work) noticing the process failing in the material it's already looking at, rather than a generic checklist item. It is also fragile in the same way the old mechanism was: it depends on an individual analyst pass choosing to say so, with no structural requirement that it does.

Edits 1 and 2 from 2026-09-10 (name the multi-review-overdue state; evaluate a scheduled notification job) are both still outstanding, and this retrospective does not have new evidence that changes the recommendation on either — they're reasonable, low-cost, still unapplied. What's new this cycle is a cheaper, complementary mechanism worth codifying alongside them (see Edit 7 below): make it a standing instruction that an analyst's Phase 6 review, on noticing a process-level pattern across the day's pieces, states a retrospective recommendation explicitly in its verdict rather than as an aside a user has to notice and act on.

## 5. Orchestration Observations

**Where delegation clearly paid off:**
- qa's sabotage-testing discipline (§2.4) — this is exactly the kind of investment that pays for itself once and keeps paying (the three-experiment proof that the atomic claim is necessary *and* sufficient, not just "the tests pass").
- The specialist/full-pipeline run on financial-report-auto-send produced two real design decisions a faster pass would likely have skipped past.
- The end-of-day convergence on `send-result-type.md`/DECISION-103: rather than closing each of the six instances as an unrelated point fix, the team correctly recognized the shape, chose a proportionate fix (two new narrow entrypoints, not a rewrite of ~18 call sites), and closed the two disclosed follow-on gaps (`SendBulkMemberEmailResult` not forwarding `blocked`; the `dev_no_api_key` no-signal case) that would otherwise have become a seventh and eighth instance.

**Where it added overhead or caused near-misses:**
- The interrupted agent leaving zero Phase 1–4 record for the per-message retry feature (§2.2) is the clearest single orchestration failure today — a money/donor/board-adjacent feature existed in the tree with no design trail, discovered only because qa happened to be dispatched next and asked "where's the writeup for this."
- Concurrent agents sharing one working tree and one dev database produced repeated, non-trivial "is this my diff or someone else's" and "why doesn't my test count match the stated baseline" reconciliation work (§2.5) — contained by individual agent discipline, not by any structural guarantee. This project's Agent tool supports `isolation: "worktree"` for exactly this scenario; it does not appear to have been used for today's concurrently-dispatched implementation work.
- The day opened with an analyst pass (`proposal-board-email.md`) whose headline finding was "the requested feature already shipped six weeks ago" — a cheap but real cost of not checking existing capability before dispatching a fresh Phase 1.

## 6. Answering the Four Questions Directly

**1. Is self-graded pipeline acceleration a root cause?** Partially, and unevenly. It is not the root cause of the flagship defect class (six same-shaped "false sent" bugs) — that one surfaced inside a Full pipeline and was caught by Phase 5, not prevented or missed by phase selection. It is a contributing cause of two of today's other defects: the privacy leak (self-declared Phase 1 skip meant no independent permissions pass ran) and the interrupted-agent gap (an extreme case — not a graded acceleration decision at all, but an orchestration failure that looks like one from the outside). The Durable-Claim Exception added today is a good, precisely-targeted response to the class it addresses, but it doesn't reach either of the other two. The general permission to accelerate is not too loose; the set of named exceptions to it is one and two items short.

**2. Why did six instances of one defect class exist simultaneously?** Because `sendEmail()`'s `success: true` on a *deliberately* successful-looking blocked path (DECISION-085, correct for ~16 of ~18 callers) was indistinguishable, at the type level, from `success: true` on a genuine delivery — for the ~2 callers that write it into a permanent record. Nothing before today made "does this caller hold a durable claim" a question anyone was structurally forced to ask. The month-long production outage was invisible for the identical reason one level down: the app reported success for work it hadn't done, and nothing distinguished "reported success" from "verified success" anywhere in the reporting surface itself (only in a human choosing to open `/admin/email-queue` and read closely — the exact same "gate degrades into silence" shape the 2026-09-10 retrospective already identified in lint/e2e/cadence). The honest answer to "what else in this codebase reports success for work it didn't do" is: audited today for the email path specifically (qa confirmed only two `new Resend(...)` call sites exist, both fixed); not audited today for any other subsystem. That's a reasonable scope boundary for one day's work, not a claim that the pattern is unique to email.

**3. What follows from qa's dual performance (unusually high value, and one payload-vs-page-load miss)?** Proposed qa.md edit in §7 below: for any change touching a public/unauthenticated route that also carries member-identifying or otherwise sensitive data, Phase 5 must include an explicit anonymous-payload check (raw response body / RSC payload, via curl or equivalent — not just rendered-DOM inspection under a signed-in or logged-out browser session), because a client-side conditional render only controls what's *displayed*, never what's *delivered*.

**4. Does the cadence system need changing?** Not urgently — this cycle's 2.1x is a real improvement over 10x and 5x. But the mechanism that actually triggered this review (an analyst's Phase 6 observation, not the session-start check) is worth codifying as a first-class, cheap addition (Edit 7) rather than treated as a one-off. The 2026-09-10 retrospective's heavier proposals (Edits 1–2) remain reasonable and still unapplied; nothing here downgrades them.
