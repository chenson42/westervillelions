## Findings

### FINDING-A (Medium) — Page-level defense-in-depth gap: 8 admin pages have no per-page auth or feature check (carry-forward)

**Status:** Carry-forward from prior code review (2026-05-27-code.md MEDIUM-1).

**Location:** The following admin pages rely exclusively on the layout gate (`src/app/(dashboard)/admin/layout.tsx`) and contain no `auth()`, `hasFeature()`, or `redirect()` calls of their own:

- `src/app/(dashboard)/admin/announcements/page.tsx`
- `src/app/(dashboard)/admin/campaigns/page.tsx`
- `src/app/(dashboard)/admin/events/page.tsx`
- `src/app/(dashboard)/admin/groups/page.tsx`
- `src/app/(dashboard)/admin/members/page.tsx`
- `src/app/(dashboard)/admin/roles/page.tsx`
- `src/app/(dashboard)/admin/testimonials/page.tsx`
- `src/app/(dashboard)/admin/users/page.tsx`

Two other admin pages (`subscriptions/page.tsx`, `sync-log/page.tsx`) call `auth()` but only check `if (!session?.user)` — no feature gate.

**What's wrong:** In the Next.js App Router, the layout gate is the first line of defense. If Next.js ever changes layout execution order, or if a misconfiguration bypasses the layout (e.g., a direct fetch to the RSC endpoint via internal tooling), the page-level data fetch runs with no auth check. This is defense-in-depth, not a directly exploitable path today.

**Impact:** Pages like `members/page.tsx` fetch the full member roster (name, email, phone, branch, memberNumber, joinDate, profilePicture) from the DB. The `users/page.tsx` fetches user account records. The `roles/page.tsx` fetches the permission structure. While the layout redirect is the practical guard, the absence of per-page checks is an architectural gap.

**Suggested fix:** Each page that renders sensitive data should add a minimal guard at the top:
```typescript
const session = await auth();
if (!session?.user?.id) redirect("/signin");
```
Higher-privilege pages (users, roles, members) should additionally check a relevant feature:
```typescript
if (!await hasFeature(session.user.id, FEATURES.MEMBERS_VIEW)) redirect("/admin");
```

### FINDING-B (Medium) — SSRF via insufficiently validated URL in zeffy-meta endpoint

**Location:** `src/app/api/admin/zeffy-meta/route.ts:15`

```typescript
if (!url || !url.includes("zeffy.com")) {
  return NextResponse.json({ error: "Invalid URL" }, { status: 400 });
}
```

**What's wrong:** The URL validation uses a substring check (`url.includes("zeffy.com")`) which can be bypassed. Any of these pass the check:

- `https://attacker.com/?x=zeffy.com` — query-string bypass
- `https://zeffy.com.attacker.com/path` — subdomain bypass
- `http://169.254.169.254/?zeffy.com` — AWS/GCP metadata endpoint
- `file:///etc/passwd?zeffy.com` — local file read (only matters in some Node environments)

An admin-authenticated user (including anyone with the default `member` role and admin dashboard access) could use this endpoint to make the server issue arbitrary outbound HTTP requests to internal services, metadata endpoints, or third-party URLs.

**Auth context:** The endpoint requires only `session?.user?.id` — no feature gate — so anyone who can access the admin dashboard can trigger it.

**Impact:** Server-side request forgery risk. The cloud platform (Vercel) does not expose EC2-style IMDS metadata endpoints, reducing the SSRF impact in production, but internal Vercel service endpoints or future infrastructure changes could be affected. The 5-second `AbortSignal.timeout` limits the DoS vector but not the data-leak vector.

**Suggested fix:** Replace the substring check with a strict hostname allowlist using the URL constructor:
```typescript
let parsed: URL;
try {
  parsed = new URL(url);
} catch {
  return NextResponse.json({ error: "Invalid URL" }, { status: 400 });
}
if (parsed.hostname !== "zeffy.com" && !parsed.hostname.endsWith(".zeffy.com")) {
  return NextResponse.json({ error: "Invalid URL" }, { status: 400 });
}
if (parsed.protocol !== "https:") {
  return NextResponse.json({ error: "Invalid URL" }, { status: 400 });
}
```

Additionally, adding `FEATURES.CAMPAIGNS_MANAGE` as a feature gate (the endpoint is only called from the campaign admin UI) would limit the attack surface to admins who actually manage campaigns.

### FINDING-C (Medium) — `cleanupExpiredTokens` uses `eq()` instead of `lte()` — would never delete expired tokens

**Location:** `src/lib/auth/password-reset.ts:121-123`

```typescript
export async function cleanupExpiredTokens(): Promise<void> {
  const now = new Date();
  await db.delete(passwordResetTokens).where(eq(passwordResetTokens.expiresAt, now));
}
```

**What's wrong:** This function uses `eq(passwordResetTokens.expiresAt, now)` — an exact timestamp equality match — which will never match any row in practice because `now` is computed at call time and will not exactly equal any stored `expiresAt`. The correct operator is `lte()` (less than or equal). Expired tokens are therefore never cleaned up by this function.

**Good news:** The function is exported but never called anywhere in the codebase (confirmed: no callsite in `src/` or `scripts/`). The `validateResetToken()` function does correctly delete individual expired tokens when they are presented (line 78). So tokens are cleaned up on use; orphaned unexpired-but-never-used tokens simply persist until someone calls this cleanup. The practical security impact is minimal — a leaked but unused token will expire and become non-functional, but it will linger in the DB.

**Suggested fix:** Fix the operator and wire up the cleanup (e.g., call it from a cron-style API route, or call it inline in `createPasswordResetToken` before issuing a new one):
```typescript
import { lte } from "drizzle-orm";
await db.delete(passwordResetTokens).where(lte(passwordResetTokens.expiresAt, now));
```

### FINDING-10 (Low) — `xlsx` remains in devDependencies with unfixable CVEs

**Location:** `package.json` devDependencies — `"xlsx": "^0.18.5"`

**What's wrong:** `xlsx` is present as a devDependency used by two one-off import scripts (`scripts/import-roster.ts`, `scripts/update-member-details.ts`). The two CVEs from the prior review (GHSA-4r6h-8v6p-xvw6 Prototype Pollution, GHSA-5pgg-2g8v-p4x9 ReDoS) still have no npm-published patch.

**Impact:** These scripts parse uploaded XLSX files (unlike the old export endpoints that only wrote XLSX). A maliciously crafted XLSX fed to these scripts could exploit the Prototype Pollution issue. However: (1) the scripts are run locally by a developer, not in the production environment; (2) the XLSX files come from Lions International roster exports, not untrusted users; (3) the scripts are not bundled or deployed.

**Suggested fix:** Migrate the two import scripts to `exceljs` (already a production dependency) and remove `xlsx` entirely. This is a low-priority local-dev concern.

## CSP / Security Headers Review (v1.18.6 Zeffy change)

The v1.18.6 commit (`345ca27`) made two targeted changes to `next.config.ts`:

1. **`frame-src`**: Added `https://www.zeffy.com` to an already-restrictive allowlist (`https://challenges.cloudflare.com https://maps.google.com https://www.google.com`). No wildcard introduced. The prior Givebutter iframe URL (`https://givebutter.com`) was not present, so this is a net-new addition rather than a replacement. Other directives (`script-src`, `img-src`, `connect-src`, etc.) were not modified.

2. **`Permissions-Policy`**: `payment=()` (blocked entirely) changed to `payment=(self "https://www.zeffy.com")`. This allows the Zeffy iframe to access the Payment Request API for Apple Pay / Google Pay. This is a minimal, specific grant — no other feature policy changed.

**Assessment:** The changes are narrow and appropriate. No wildcard origins were introduced. `default-src 'self'` remains the fallback. `script-src` still requires explicit allow-listing. The `'unsafe-inline'` and `'unsafe-eval'` in `script-src` are pre-existing (required by Next.js/React) and not new to this commit.

**One note for future hardening:** `script-src 'unsafe-eval'` is required today for Next.js 16 development mode but may be removable in production builds. This is a pre-existing hardening opportunity, not introduced by the Zeffy change.
