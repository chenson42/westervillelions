## Findings

### FINDING-NEW-1 (MEDIUM) — `allowDangerousEmailAccountLinking` risk increased by Ledger

**File:** `src/lib/auth/index.ts:24`

**Description:** `allowDangerousEmailAccountLinking: true` on the Google provider means any user who controls a Google account for a given email address can silently merge into an existing portal account. With the Ledger system now recording real financial transactions linked to `session.user.id` (as `recordedByUserId`, `approvedByUserId`, `reviewedByUserId`), a successful account merge gives the attacker the full financial footprint of the victim's account — including the ability to record transactions, approve disbursements (if victim has LEDGER_APPROVE), and view donor PII (if victim has LEDGER_RECORD).

This was flagged as LOW in the prior two cycles because the membership-only portal had limited financial consequence. The Ledger changes the risk profile. The flag remains necessary for the `@westervillelions.org` auto-link flow, but it is not documented in CLAUDE.md or in a DECISION entry.

**Fix:** Either (a) document the accepted risk in `docs/decisions.md` with a concrete threat model entry, or (b) restrict `allowDangerousEmailAccountLinking` to `@westervillelions.org` domain only (NextAuth v5 allows per-provider `allowDangerousEmailAccountLinking` with a custom `authorize` callback). At minimum, document the decision so future reviewers understand the trade-off.

### FINDING-NEW-2 (MEDIUM) — Dues CSV export uses `csvCell()` (no formula-injection guard)

**File:** `src/app/api/admin/dues/export/route.ts:13-19`

**Description:** The dues CSV export uses a local `csvCell()` function that handles RFC 4180 quoting (commas, double-quotes, newlines) but does NOT prepend a tab when the first character is `=`, `+`, `-`, or `@` (the OWASP formula-injection defence). The ledger transaction export (`/api/admin/ledger/export/route.ts`) correctly uses `csvCellSafe()` from `src/lib/csv-safe.ts` for user-supplied free-text columns. The dues export does not.

Columns at risk: `lastName`, `firstName`, `email`, `duesCategory`, and `notes` — all can contain treasurer-entered free text. In practice, a member name like `=CMD|' /C calc'!A0` would pass through unguarded.

**Fix:** Replace the local `csvCell()` call with `csvCellSafe()` from `@/lib/csv-safe` for columns that contain user-supplied text (`lastName`, `firstName`, `email`, `duesCategory`, `notes`). Pure-numeric and enum columns can continue using the raw variant.

```typescript
// Before
csvCell(m.lastName),
csvCell(m.firstName),
csvCell(m.email),

// After
import { csvCellSafe } from "@/lib/csv-safe";
csvCellSafe(m.lastName),
csvCellSafe(m.firstName),
csvCellSafe(m.email),
```

### FINDING-NEW-3 (MEDIUM) — Impact dashboard exposes `party` (payee names) to all linked members

**File:** `src/lib/ledger-queries.ts:1788-1816` and `src/app/members/impact/page.tsx:205-227`

**Description:** The "Recent Named Gifts" section on `/members/impact` displays the `party` field from expense transactions (e.g., "Westerville Food Pantry $500.00 · Community support · June 15, 2026"). The `party` field is treasurer-entered free text naming the payee. When `philanthropyVisibility = 'members'` (the more open setting), every linked member — including ordinary members with no ledger access — can see all recent payee names and amounts.

This is an intentional UX choice (DECISION-024), but it is a meaningful exposure: a member could learn that a specific named individual or organization received funds. The Phase 3 design notes say "null-party rows are excluded" (DECISION-024) but does not address whether non-null party values are appropriate to show unfiltered to all members.

This is not a code bug — the design explicitly selects `party IS NOT NULL` for the recent gifts list. But it was not explicitly reviewed as a PII question in Phase 1 of the impact increment.

**Fix:** Document the intentional decision: if the board is comfortable exposing payee names to all members, add a DECISION entry confirming this is accepted. If not, filter the recent gifts query to exclude individual-name entries (e.g., only show organizational payees via an `is_organization` flag, or suppress the recent gifts section when `philanthropyVisibility = 'members'`).

### FINDING-NEW-4 (LOW) — `PATCH /api/admin/ledger/transactions/[id]/acknowledge` returns `letterStorageKey` in response body

**File:** `src/app/api/admin/ledger/transactions/[id]/acknowledge/route.ts:328-331`

**Description:** The PATCH (mark-sent) handler returns `.returning()` from the `ledger_acknowledgments` table and sends the full row as JSON:

```typescript
const [updated] = await db
  .update(ledgerAcknowledgments)
  .set(patch)
  .where(eq(ledgerAcknowledgments.id, existingAck.id))
  .returning();

return NextResponse.json(updated); // leaks letterStorageKey
```

The `ledger_acknowledgments` table has a `letterStorageKey` column (an opaque storage key, `src/lib/db/schema.ts:702`). Returning the full row sends this key to the browser. DECISION-020 specifies that storage keys must never be sent to the browser — receipts and letters must only be accessible via the server-side proxy routes.

This is a consistency violation with the established pattern (admin reimbursement routes strip `receiptStorageKey` before returning, both in list and single-item responses).

**Severity: LOW** (the key is opaque — a UUID-prefixed path, not a signed URL — and the caller already has LEDGER_RECORD to reach this endpoint; the key is not directly useful without server-side storage access).

**Fix:** Strip `letterStorageKey` before returning:

```typescript
const [updated] = await db
  .update(ledgerAcknowledgments)
  .set(patch)
  .where(eq(ledgerAcknowledgments.id, existingAck.id))
  .returning();

const { letterStorageKey: _k, ...safe } = updated;
return NextResponse.json(safe);
```

### FINDING-NEW-5 (LOW) — Orphan receipt blobs accumulate indefinitely

**File:** `src/app/api/members/reimbursements/[id]/route.ts:157-159` and `src/app/api/members/reimbursements/route.ts:237-240`

**Description:** When a member withdraws a reimbursement or edits their request (replacing the receipt), the old `receiptStorageKey` blob is never deleted from storage. This is explicitly documented as a known deferral in the Phase 3 edge cases (the comment says "Orphan cleanup is deferred to inc3"). However, `inc3` (compliance/990) shipped without a receipt cleanup mechanism, and `inc6b` (donors+acknowledgments) is the last increment. The cleanup is now permanently deferred.

In Vercel Blob, orphan files accumulate storage cost. In local dev, `.receipt-store/` grows without bound.

**Fix:** Implement a cleanup step in the `DELETE` handler (withdraw) that calls `getReceiptStorage().delete(reimb.receiptStorageKey)` before returning. For the edit (PATCH) case, delete the old key when a new `receiptStorageKey` is provided. Both are fire-and-forget (log failure, don't block the operation).

## Healthy Patterns — What's Working Well

**Receipt proxy design is solid.** Both admin and member receipt proxy routes (`/api/admin/ledger/reimbursements/[id]/receipt` and `/api/members/reimbursements/[id]/receipt`) correctly stream file bytes server-side and never send the storage key or blob URL to the browser. The pattern is consistent with DECISION-020.

**Opaque key validation is correct.** The `receiptStorageKey` regex (`/^receipts\/[0-9a-f-]{36}\/[a-zA-Z0-9._-]{1,150}$/`) is validated in both the upload route and the submit route, preventing path traversal or injection via a crafted key.

**Magic-byte validation is correct.** `validateMagicBytes()` checks actual file signatures (PDF, JPEG, PNG) rather than trusting the client-supplied `Content-Type`. This is the right defence against polyglot files. Coverage is 100% per the 2026-06-25 test log.

**Approval gate is correctly server-side.** The `disbApprovalThresholdCents` check in `POST /api/admin/ledger/transactions` is entirely server-side — the `status` field is derived from the amount and settings, never from client input. Comment at line 202: "Derive status SERVER-SIDE — ignore any client-supplied `status` field." Self-approval blocks are present on both the transaction approve/reject routes and the reimbursement approve/reject PATCH.

**Donor PII gate (DECISION-025) is implemented correctly.** `GET /api/admin/ledger/acknowledgments` runs two permission checks: `hasAnyFeature([VIEW, RECORD, MANAGE])` for access, then `hasFeature(LEDGER_RECORD)` to set `includePii`. The query strips `donorId` and `donorName` when `includePii = false`. The acknowledgment-summary route correctly bifurcates this. The donor list and donor-detail routes both gate on `LEDGER_RECORD`.

**Enumeration guard on donor IDs is correct.** `GET /api/admin/ledger/donors/[id]` returns 403 (not 404) when the caller lacks LEDGER_RECORD, preventing ID enumeration for PII-sensitive donor records. The acknowledgment letter proxy route follows the same pattern.

**Two-fund firewall is intact.** Fund-to-entity cross-validation is present in the transaction POST and transfer handler. Transfers query only funds within `entityId`. The fund-entity association check is enforced server-side before inserting.

**Double-pay guard is atomic.** The `pay` action in `PATCH /api/admin/ledger/reimbursements/[id]` uses a DB transaction with `.where(eq(status, 'approved'))` on the update, rolling back with `DOUBLE_PAY` if the status changed between check and write.

**Member dues firewall is correct.** `GET /api/members/dues` derives `memberId` exclusively from `session.user.memberId` (JWT), never from query parameters. `getMemberDuesForUser()` accepts only the caller's own memberId. No way for a member to request another member's dues.

**Member receipt ownership enforcement is correct.** `GET /api/members/reimbursements/[id]/receipt` returns 404 (not 403) for IDs belonging to other members. The ownership check (`reimb.submittedByMemberId !== session.user.memberId`) is evaluated after auth, preventing existence leaking via differential timing.

**CSV injection guard is applied to ledger exports.** `csvCellSafe()` is used for all user-supplied free-text columns in the transaction and 990-prep exports (Category, Party/Payee, Memo, lineGroup). The OWASP formula-injection prefix (`\t`) is prepended when the first character is `=`, `+`, `-`, or `@`. Test coverage: 12 `csvCellSafe` cases per the 2026-06-25 test log.

**Dependency CVE status:** `pnpm audit --prod --audit-level=high` returns **0 high / 0 critical** (1 low, 1 moderate, both transitive). Per the 2026-06-26 dependency review, all high CVEs are closed. No new high or critical CVEs introduced by the Ledger increments or their dependencies (`@vercel/blob` vetted clean in the 2026-06-26 review).

**OAuth / NextAuth session shape is correct.** JWT strategy correctly loads `roles`, `features`, `memberId`, and `isActive` from DB on sign-in and `trigger === 'update'`. The 60-second permission cache in `permissions-server.ts` is an acceptable TTL for a club-size application. Google Group sync credentials (`GOOGLE_GROUPS_REFRESH_TOKEN`) are environment variables, never committed.
