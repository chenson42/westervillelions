# 2026-08-12 — PII Scrub for Public Release

**Trigger:** The private repo is being retained as an archive; the treasurer is starting a fresh
public repository from a scrubbed copy of the working tree. This is an ad hoc scrub, not a
scheduled 30-day security review (though it satisfies that review's PII-sweep scope for this
cycle — see `docs/reviews/log.md`). Git history is out of scope; only the working tree needed
to be clean.

## Scope and policy

Ban: personal email addresses, phone numbers, home/street addresses, and anything tying a named
non-officer person to money, dues, health, or personal circumstances. Allow: club-domain
addresses (`board@`, `club@`, `info@`, `treasurer@`, `noreply@westervillelions.org`), officer
names in a governance context, and `example.com`/`example.invalid`/`*.test` in fixtures. Full
policy is now codified in `CLAUDE.md` → *No Personal Data in the Repository* and enforced going
forward by `/pre-push`'s Personal Data Sweep step (both added in commit `7d521f6`, prior to this
scrub).

**9 personal email addresses, ~73 occurrences**, across migrations, scripts, docs, and

officers and members, including one `+alias` variant used for QA testing. Deliberately not
re-listed here in cleartext (a doc that says "we removed address X" would just reintroduce X into
the public repo it's describing).

**Two additional findings from a follow-up sweep**, not on the original address list:

  `docs/treasurer-todo.md`, and `scripts/import-quicken-ledger.ts`, tied to two deleted test dues

- A single line in `docs/work-log/2026-07-21-impact-gift-public-note.md` naming three 2025

No phone numbers or street/home addresses were found outside the public glasses/plastics

## The hard part: migrations that hardcode a person's email

Three migrations used a real address in a `WHERE` clause to grant a role or set billing data:

- **`0040_dues_tracking.sql`** — granted the `treasurer` role to two named people by email.
- **`0069_ledger_budget_permissions.sql`** — granted `budget_committee` to one named person by
  email.
- **`0043_dues_family_members.sql`** — set `dues_category = 'family'` on three named members by
  email. This one doesn't grant access; it's billing data.

**Approach chosen: environment-variable substitution, done in the migration runner.**
`drizzle/run-migrations.mjs` (read first, per the task's own instruction — it has no templating
today, just `readFileSync` + `sql.unsafe(content)`) now does simple string substitution before
executing each file: any occurrence of the literal token `{{SEED_ADMIN_EMAIL}}` is replaced with
`process.env.SEED_ADMIN_EMAIL` (a single quote in the value is escaped so it can't break out of
the SQL string literal). Left unset, it substitutes to `''`, and `WHERE u.email = ''` matches no
real user — a guaranteed no-op, same idempotency guarantee the migrations already had.

`0040` and `0069` were rewritten against this token. `0040` was also extended to grant `admin`,
not just `treasurer` — there was previously no migration anywhere in the repo that could bootstrap
a fresh install's first admin (the existing production admin was granted by hand, outside any
migration). This closes that gap: a fresh install now becomes usable by setting
`SEED_ADMIN_EMAIL` in `.env.local` after a first sign-in and re-running `pnpm db:migrate`,
documented in `SETUP.md` step 7, `.env.example`, and `CLAUDE.md` → Environment Variables.

`0043` was **not** parameterized. It isn't an access grant, and the recommended alternative in the
task ("drop the person-specific seed and document the alternative") fit better here: production
already carries the `dues_category = 'family'` values this migration set (removing the seed
doesn't undo prior runs), and the club already has a purpose-built admin UI for this exact field
(`src/components/admin/dues-category-control.tsx`, `PATCH /api/admin/dues/[memberId]/category`).
The file is kept only so migration numbering stays contiguous, replaced with a comment and a
harmless `SELECT 1;`.

Logged as `DECISION-089` in `docs/decisions.md`.

## Scripts

Several one-off scripts under `scripts/` resolved an actor/creator user by one of the same
hardcoded personal emails, to attribute `recorded_by_user_id`, `created_by`, or an audit-log actor.
All now read `process.env.SCRIPT_OPERATOR_EMAIL` and throw a clear error if it's unset — these are
manually invoked treasury/admin scripts, not something a fresh install runs unattended, so
requiring the operator to set an env var (documented in `CLAUDE.md`) is the right failure mode
rather than a silent no-op:
`add-kroger-rewards-category.ts`, `backfill-dues-ledger.ts`,
`close-out-historical-acknowledgments.ts`, `deactivate-unused-categories.ts`,
`import-quicken-ledger.ts`, `june-close-correction.ts`, `port-ledger-dev-to-prod.ts`,
`add-2026-27-meeting-schedule.ts`, `add-bmx-volunteer-events.ts`.

Two roster scripts (`import-roster.ts`, `sync-roster.ts`) special-cased one real household's
shared email address to give both members a distinct login. This isn't an access grant and a
fresh install's own roster file won't have this specific case, so it now reads three optional env
vars (`SHARED_HOUSEHOLD_EMAIL`, `_ALT`, `_ALT_FIRST_NAME_MATCH`) and is a no-op — not a hard
error — when they're unset.
