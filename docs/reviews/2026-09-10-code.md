### HIGH-1: The exact duplication class CLAUDE.md's mandate was written about is still open, and has grown, not shrunk

CLAUDE.md's "Duplication Is a Review Finding" section names three specific counts from the 2026-08-12 incident: **from-address fallback × 12, HTML escaper × 6 (one omitted, causing an unescaped-text send to the whole board), app-URL fallback × 8.** As of this review:

`src/app/api/contact/route.ts:39`, `admin/ledger/reimbursements/[id]/route.ts:155`, `admin/ledger/transactions/route.ts:383,693`, `admin/minutes/[id]/email/route.ts:74`, `admin/social-requests/[id]/decide/route.ts:111`, `admin/events/[id]/announce/route.ts:285`, `admin/proposals/[id]/decide/route.ts:146`, `membership-applications/route.ts:87`, `members/reimbursements/route.ts:169`, `members/social-requests/[id]/submit/route.ts:99`, `members/proposals/[id]/submit/route.ts:111`, `suggestions/route.ts:48`, `lib/members.ts:122`, `lib/auth/index.ts:195`.

**`process.env.NEXTAUTH_URL` fallback — 18 independent copies across 17 files** (was 8; re-verified against the full pattern `process\.env\.NEXTAUTH_URL`, not just the `?? ` spelling, which is why this count is higher than an earlier pass in this same review found):
`admin/ledger/reimbursements/[id]/route.ts:156`, `admin/ledger/transactions/route.ts:401,711`, `admin/dues/reminders/route.ts:169`, `admin/social-requests/[id]/decide/route.ts:112`, `admin/events/[id]/announce/route.ts:54`, `admin/proposals/[id]/decide/route.ts:147`, `members/reimbursements/route.ts:171`, `members/social-requests/[id]/submit/route.ts:100`, `members/proposals/[id]/submit/route.ts:112`, `api/events/[id]/ics/route.ts:79`, `members/events/page.tsx:47`, `events/page.tsx:89`, `events/[id]/page.tsx:148,194`, `lib/members.ts:119`, `lib/ledger-acknowledgment-letter-queries.ts:559` (uses `||` instead of `??` — same bug class, different operator), and `api/auth/forgot-password/route.ts:25` — **this last one has no fallback at all**: `` `${process.env.NEXTAUTH_URL}/reset-password?token=${token}` ``. If `NEXTAUTH_URL` were ever unset, every password-reset email would link to `undefined/reset-password?token=...`. `NEXTAUTH_URL` is a required env var per CLAUDE.md so this isn't an active incident, but it is the exact "one copy quietly missing the guard" shape the 2026-08-12 escaper incident is remembered for — worth folding into the same `email-compose.ts` fix as a required, not optional, parameter.

There are also two different non-empty fallback values in use where a fallback exists at all — `""` (9 call sites: everything under `/api/admin/ledger`, `/api/admin/dues`, `/api/admin/social-requests`, `/api/admin/proposals`, and their `/api/members/*` counterparts) vs `"https://westervillelions.org"` (8 call sites: the event/ICS pages, `announce`, and `lib/members.ts`) — its own small inconsistency, since an admin-side email link with the `""` fallback would render as a bare `/admin/ledger/approvals` path (relative, breaks outside a browser context like an email client) while the public-page fallback correctly produces an absolute URL.

**`escapeHtml` — 4 independent implementations, not converged to the shared one:** `src/lib/html-escape.ts:34` (the canonical, newest copy — 4-char escape set), `src/lib/proposals.ts:441` (`escapeProposalHtml`, same 4-char set), `src/lib/dues-reminders.ts:42` and `src/lib/ledger-acknowledgment-letter.ts:341` (both 5-char — they additionally escape `'`). The two escape sets genuinely disagree, which is a correctness inconsistency on top of the duplication. This one is unusually well tracked already: `html-escape.ts`'s own doc comment names all three prior copies, says explicitly *"this file does NOT replace the three existing copies... belongs to the architect's 30-day code review, which already owns exactly this class of finding"* — and backlog **B-46** exists for it. This review is that pass; consolidating is the recommended action, not a new discovery.

**Proposed consolidation:**
- `escapeHtml` → delete `proposals.ts:441`, `dues-reminders.ts:42`, `ledger-acknowledgment-letter.ts:341`; every caller imports `src/lib/html-escape.ts`. Decide the escape set once (recommend keeping `'` → `&#39;`, the stricter of the two, since it's already proven safe in two features) and drop the double-encoding review needed for `&` either way.
- From-address / app-URL fallbacks → one module, e.g. `src/lib/email-compose.ts` (already floated by the `ledger-acknowledgment-letter.ts:341` comment as B-46's target) exporting `getFromEmail()` and `getAppUrl()` — the latter with a required, non-optional fallback so the `forgot-password/route.ts` gap above can't recur. Fifteen and eighteen call sites shrink to one function call each; a future change to the from-address or a switch away from `NEXTAUTH_URL` becomes a one-line edit instead of a grep-and-replace across 30+ files.

### HIGH-1b (same finding, different domain): local date formatters — 37 files, the safe fix triplicated 13× rather than shared

37 files define their own `formatDate`/`formatYMD`. Classified by pattern:

- **13 files** implement the *identical* safe split-and-reconstruct pattern (`const [y,m,d] = dateStr.split("-").map(Number); new Date(y, m-1, d).toLocaleDateString(...)`), byte-for-byte the same 7-line function, only the month format (`"short"`/`"long"`) differs: `ack-queue.tsx:30`, `acknowledgment-letter-selector.tsx:41`, `reconciliation-matching-grid.tsx:21`, `members/dues/page.tsx:16`, `members/impact/page.tsx:19`, `admin/ledger/approvals/page.tsx:17`, `admin/dues/[memberId]/page.tsx:22`, `reconciliation-match-picker.tsx:15`, `uncashed-checks-panel.tsx:10`, `reconciliation-session-list.tsx:9`, `unremitted-deposits-panel.tsx:10`, `reconciliation-create-from-bank-line-dialog.tsx:24`, `impact-by-cause.tsx:40`.
- **3 more** use a `T00:00:00`-suffix variant of the same fix: `sent-ack-list.tsx:17`, `members/social-requests/[id]/page.tsx:23`, `admin/social-requests/[id]/page.tsx:20`.
- **`ack-queue.tsx`'s own comment names the other two** ("mirrors `formatYMD()` in acknowledgment-letter-selector.tsx and `formatDate()` in reconciliation-matching-grid.tsx") — the duplication was noticed at write time and consciously left unconsolidated, three separate times.
- The remaining ~21 files operate on `Date | string` inputs that are genuinely timestamps (`createdAt`/`decidedAt`), not date-only strings — those are lower risk (the naive-UTC bug needs a date-only string parsed with a bare `new Date()`) but are still 21 more copies of the same 3-line `toLocaleDateString` wrapper.

No shared date-formatting helper exists anywhere in `src/lib/` today (`src/lib/utils.ts` has `formatEmailList`/`formatFileSize` but no date helper). Given this project's specific, repeated history with naive-timestamp-as-UTC bugs (project memory: two prior incidents plus this week's), the risk here isn't just duplication-as-tidiness — it's that the *correct* fix for a real, recurring bug class was independently reinvented 13+ times instead of being written once and imported.

**Proposed consolidation:** `src/lib/date-format.ts` exporting `formatYMD(dateStr: string, style: "short" | "long" = "short")` (the safe split-parse, covering the 13+3 files above) and `formatTimestamp(d: Date | string, style)` for the genuine-timestamp call sites. This turns the correctness property ("never construct `new Date()` from a bare date-only string") into something enforced by one function instead of an unenforced convention 16+ authors have to each remember.

### MEDIUM-1: `sendEmail()` hand-looped over multiple recipients instead of `sendBulkMemberEmail()` — 2 occurrences, same file

CLAUDE.md is explicit: *"Bulk member mail must go through `sendBulkMemberEmail()` — never a hand-rolled loop over `sendEmail()`."* `src/lib/email.ts` defines `sendBulkMemberEmail()` for exactly this. Two call sites in `src/app/api/admin/ledger/transactions/route.ts` don't use it:

- **Line ~391-392** (pending-transaction approval-request notification): `for (const email of approverEmails) { await sendEmail({ to: email, ... }); }`
- **Line ~702-703** (pending-transfer/sweep approval-request notification): identical shape, `for (const email of approverEmails) { await sendEmail(...) }`

`approverEmails` comes from `getEmailsForFeature(FEATURES.LEDGER_APPROVE)` — a genuine multi-recipient list (every LEDGER_APPROVE holder), the same shape `sendBulkMemberEmail()` exists to handle. This is exactly the class of call site the 2026-08-12 disbursement-notification incident (documented in CLAUDE.md's *Outbound Email Is Deny-By-Default* section) came from — it mailed 16 real board members from a QA run via a path "neither a distribution list nor a bulk send," which is precisely what a hand-rolled loop looks like from the outside. Recommend migrating both call sites to `sendBulkMemberEmail()`.

### MEDIUM-2: Permission-gate boilerplate repeated across ~68 admin pages, with an existing helper that doesn't fit the shape

Every one of the 70 `page.tsx` files under `src/app/(dashboard)/admin/` (verified — none are missing the check) repeats the same 4-line pattern by hand:
```ts
const session = await auth();
if (!session?.user?.id) redirect("/signin");
const canX = await hasFeature(session.user.id, FEATURES.X);
if (!canX) redirect("/access-pending" | "/admin");
```
`src/lib/permissions-server.ts:114` already exports `requireFeature(userId, feature): Promise<void>` — but it *throws* rather than redirecting, so it doesn't fit this call shape, and **`requireFeature()` has zero callers outside its own file.** Dead-on-arrival API: written for a pattern the codebase doesn't use.

This is boilerplate, not logic — the redirect target varies (`/signin` is universal, but the failure redirect varies between `/access-pending` and `/admin`), so a shared helper needs a `redirectTo` param. Proposed: `requireFeatureOrRedirect(feature: FeatureName, redirectTo = "/access-pending")` in `permissions-server.ts`, replacing `requireFeature()` (which has no callers to migrate) and collapsing each page's 4 lines to 1. Given the volume (68 pages) and that CLAUDE.md's proxy-regression history (5 prior lockout incidents) is specifically about this exact boilerplate drifting out of sync, this is worth doing — but note it's boilerplate consolidation, not a correctness bug today: every page currently gates correctly (see Invariants below).

### MEDIUM-3: Fiscal-year-from-date-string parsing triplicated — self-aware, but at the CLAUDE.md threshold

`getFiscalYear(date: Date)` in `src/lib/fiscal-year.ts` is a genuine single source of truth for the Jul–Jun boundary math — no drift risk there. But the wrapper that turns a `"YYYY-MM-DD"` transaction-date string into a fiscal year via `new Date(txnDate + "T00:00:00")` (the safe, non-UTC-shifted parse) is implemented identically three times:

- `src/lib/budget-context-panel-ui.ts:36-40` (`deriveFiscalYearFromTxnDate`, exported + unit-tested)
- `src/components/admin/ledger/budget-line-picker.tsx:42-47` (inline, not exported)
- `src/components/admin/ledger/transaction-form.tsx:~288-291` (inline, not exported)

This is documented, not accidental — `budget-context-panel-ui.ts`'s comment states the design decision explicitly: *"it's already duplicated twice in this codebase without complaint, and a third inline copy is more honest than introducing a one-line-saving abstraction three call sites deep."* That reasoning has some merit (the two-line parse-then-delegate is genuinely trivial, and the actual FY math stays centralized), but three identical copies is CLAUDE.md's literal trigger ("more than two places"). Recommend extracting the wrapper too — `deriveFiscalYearFromTxnDate` already exists, exported and tested; `budget-line-picker.tsx` and `transaction-form.tsx` should just import it rather than re-deriving inline. Low urgency (the risk of the *math* drifting is near-zero since `getFiscalYear` is shared), but it's a two-line fix with a positive net line count once you count the doc comments justifying the non-fix.

## Deferred Items — Verdict

Both `docs/work-log/2026-09-10-budget-context-panel-compiler-findings.md` and the `src/app/(dashboard)/admin/ledger/page.tsx` `react-hooks/error-boundaries` suppression are correctly still-deferred; neither should be rushed.

**`budget-context-panel.tsx:114`** — the render-body ref write is a deliberate staleness guard for a concurrent-fetch race (Flow 3, documented in-file), and moving it into `useEffect` changes *when* the guard updates relative to render, in money-adjacent code, without a proven-safe replacement. Two independent sessions today reached the same conclusion and the second correctly backed out its prototype rather than land a second fix. **Status: correctly deferred, not urgent.** No evidence of an active bug — the compiler warning is about a pattern the React team wants eliminated going forward, not a symptom of a live defect. Route it through Phase 1-3 on a normal cadence, not as a hotfix.

**`ledger/page.tsx:80`** — I checked whether the error-boundary gap this comment describes is wider than one file: **`grep -rn "react-hooks/error-boundaries" src/` returns exactly this one line**, and **there is no `error.tsx` anywhere under `src/app`** — zero Next.js route-segment error boundaries in the entire application. So the gap is real and *is* wider than the comment implies: any render-phase throw in any server component, anywhere in the app, currently falls through to Next's default unstyled error page, not just `<LedgerDashboard>`. The `try/catch` in `ledger/page.tsx` does correctly cover its dominant failure mode (the `Promise.all` fetches) per its own comment — so this isn't a live bug, it's a coverage gap for a failure mode (render-phase throw) that hasn't been observed. **Recommendation, separable from the FY-staleness question above:** a single `src/app/(dashboard)/admin/error.tsx` (or `src/app/error.tsx`) is a small, low-risk addition that closes this gap for the *entire* admin area at once, independent of and much cheaper than the compiler-suppression fix — worth doing on its own track rather than waiting on the harder budget-context-panel decision it's currently bundled with in the same work-log note.
