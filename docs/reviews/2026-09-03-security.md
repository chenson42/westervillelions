## HIGH

### H1 — Admin detail/edit sub-pages have no page-level feature gate; a real exploit chain exposes member home address/phone

**Files (no `auth()`/`hasFeature()` call anywhere in the page source):**
- `src/app/(dashboard)/admin/members/[id]/page.tsx` — renders full member record: phone, home address, city/state/zip
- `src/app/(dashboard)/admin/users/[id]/page.tsx` — user account + role list
- `src/app/(dashboard)/admin/events/[id]/page.tsx` — full RSVP table: attendee names + emails
- `src/app/(dashboard)/admin/campaigns/[id]/page.tsx`, `groups/[id]/page.tsx`, `testimonials/[id]/page.tsx`, `announcements/[id]/page.tsx`
- Matching `new/` pages for members, events, campaigns, testimonials, announcements, groups (lower-risk — no existing-record data to leak, but same gap in principle)

**Background:** 2026-05-27 and 2026-06-24 (`FINDING-A`) flagged 8 admin **list** pages (`members/page.tsx`, `events/page.tsx`, etc.) as relying only on `admin/layout.tsx`'s coarse "holds at least one admin feature" gate. That was fixed — `src/lib/admin-page-feature-gates.test.ts` now fails CI if any top-level `/admin/<segment>/page.tsx` lacks its own `hasFeature()`/`hasAnyFeature()` call with an enforcing `redirect()`. I confirmed every current top-level list page passes it.

**What's new:** the fix only covers the top-level segment directory (`src/app/(dashboard)/admin/<segment>/page.tsx`). The **detail/edit sub-routes one level down** (`<segment>/[id]/page.tsx`, `<segment>/new/page.tsx`) were never in scope of the 2026-06-24 finding or the regression test the fix produced (`topLevelAdminSegments()` walks `readdirSync(ADMIN_DIR)` — directories, not nested routes). They still rely solely on `admin/layout.tsx`'s `canAccessAdminArea()` check, which the layout's own comment documents as admitting "a user who holds a narrower grant (e.g. `budget.edit`, without `admin.dashboard`)" — i.e., **any single admin-area permission, regardless of relevance, is sufficient to reach every one of these pages.**

Unlike the 2026-06-24 finding (list pages, where the 2026-06-27 downgrade reasoned a blocked user would "see empty state... from the route-handler layer"), these detail pages fetch and render PII **directly via server-side DB query in the page component itself** — there is no route handler in the read path to fall back on. The page body runs to completion and streams the HTML before any write is attempted, so the "empty state" mitigation the 2026-06-27 downgrade relied on does not apply here.

**Concrete exploit chain (no privilege escalation needed, no ID guessing required):**
1. `src/app/about/page.tsx` renders the public leadership grid using each board member's real `members.id` (UUID) in an `<img src="/api/public/members/{memberId}/photo">` tag — visible in the public page's HTML source to anyone, signed in or not (see L5 below).
2. An attacker who holds **any** single admin-area permission — e.g. only `testimonials.manage`, one of the lowest-trust admin roles in the system — signs in and navigates directly to `/admin/members/{that UUID}`.
3. The page renders that board member's phone number and home address in full, with no `MEMBERS_VIEW`/`MEMBERS_EDIT` check anywhere in the request path.

The same pattern applies to `/admin/events/{id}` for any **public** event (its ID is visible in the public `/events/{id}` URL) — RSVP names and emails for that event are readable by any admin-tier account regardless of `EVENTS_EDIT`.

**Fix:** add the same `hasFeature()`/`hasAnyFeature()` + `redirect()` pattern the top-level pages already use to every `[id]/page.tsx` and `new/page.tsx` under `src/app/(dashboard)/admin/`, using the same feature the corresponding top-level list page requires (`MEMBERS_VIEW`/`MEMBERS_EDIT` for members, `EVENTS_EDIT` for events, etc.). Then extend `admin-page-feature-gates.test.ts`'s `topLevelAdminSegments()` walk to recurse into `[id]`/`new` sub-directories (or add a second, explicit assertion list) so this class of regression fails CI the same way the list-page version now does — this is exactly the "closes the loophole the test itself documents as unclosed" pattern the existing test's own header describes, one level deeper than it currently reaches.

## MEDIUM

### M1 — `allowDangerousEmailAccountLinking: true` still unmitigated (carry-forward, 2nd cycle)

**File:** `src/lib/auth/index.ts:25`, Google provider config.

Unchanged since the 2026-06-27 review, which first flagged this. Confirmed by direct read: the flag is still `true`, and there is no `email_verified` (or equivalent) check anywhere in `src/lib/auth/index.ts` — the `signIn` callback only checks `isActive` on the linked member record, not whether the Google-asserted email has actually been verified by Google before silently linking it to an existing `users` row. Practically: anyone who can get Google to hand them an OAuth grant for an *unverified* address matching an existing member's email can link into that member's account and inherit their session — including, since June, access to Ledger donor data, reimbursements, and proposals. The risk profile has grown with the feature surface behind it, not shrunk. **Fix:** check `profile.email_verified === true` in the `signIn` callback before permitting the linking path, or drop the flag and require an explicit admin-initiated linking action instead.

### M2 — Dues CSV export still lacks the formula-injection guard (carry-forward, 3rd cycle)

**File:** `src/app/api/admin/dues/export/route.ts:13-19`

Unchanged from the 2026-06-27 `FINDING-NEW-2`. The route still defines a local `csvCell()` that does RFC 4180 quoting but never prepends the OWASP formula-injection guard tab for values starting with `=`, `+`, `-`, `@`, instead of importing the shared `csvCellSafe()` from `src/lib/csv-safe.ts` (which the ledger export already uses correctly). `docs/decisions.md` (~line 3042, DECISION-023's rationale) explicitly notes this was deferred with "that surface will be caught in the next security review" — this is that review, and it's still open. The decision's mitigating context is real (dues-export name/email fields are treasurer-entered via `MEMBERS_EDIT`, not self-service member input, so exploitation needs a malicious or compromised admin account, not an anonymous attacker) — but the fields are still free text, the shared safe helper already exists, and this is now a second implementation of the same escaping logic per CLAUDE.md's duplication rule. **Fix:** swap `csvCell` → `csvCellSafe` from `@/lib/csv-safe` for `lastName`, `firstName`, `email`, `duesCategory`; delete the local `csvCell`.

### M3 — Admin image upload trusts client-supplied MIME type and filename extension; no magic-byte check

**File:** `src/app/api/admin/upload/route.ts`

Gated correctly on `CAMPAIGNS_MANAGE` (only caller is `campaign-form.tsx`), but the content check is `ALLOWED_TYPES.includes(file.type)` — `file.type` is the browser-set `Content-Type` of the multipart part, which is trivially spoofable via a raw request. The stored filename's extension is taken directly from the client-supplied `file.name` (`file.name.split(".").pop()`), also unvalidated. The result is written to `public/uploads/campaigns/<uuid>.<attacker-chosen-ext>` — a publicly-served static path. This differs from the reimbursement-receipt upload pattern, which does real magic-byte validation. Exploitation requires an already-compromised or malicious `CAMPAIGNS_MANAGE` account, which bounds the severity, but a mismatched extension + spoofed MIME on a public static path is a stored-content-type-confusion primitive worth closing. **Fix:** validate actual file bytes (reuse the existing receipt magic-byte helper) and derive the stored extension from the validated content type, not from `file.name`.

### M4 — Impact dashboard payee names to all members (carry-forward, unresolved design question)

**File:** `src/lib/ledger-queries.ts` (`getPhilanthropy()`) / `src/app/members/impact/page.tsx`

Unchanged from 2026-06-27 `FINDING-NEW-3`. When `philanthropyVisibility = 'members'`, the "Recent Named Gifts" section still shows the treasurer-entered `party` (payee) field to every linked member, with no distinction between an organizational payee and a named individual. `DECISION-024` documents the null-`party` exclusion but never answers the PII question the prior review raised. Still not a code bug — an intentional design surface that was never explicitly signed off on as a privacy tradeoff. **Fix (unchanged from last cycle):** either add a `docs/decisions.md` entry confirming the board is comfortable with this exposure, or gate individual-looking payee names out of the `members`-tier view.

## LOW

### L1 — `letterStorageKey` still returned by acknowledge PATCH (carry-forward, unchanged)

`src/app/api/admin/ledger/transactions/[id]/acknowledge/route.ts` (~line 496) still does `return NextResponse.json(updated)` on the full `.returning()` row, including the opaque `letterStorageKey`. Same fix as 2026-06-27: destructure it out before responding, matching the reimbursement routes' existing pattern.

### L2 — Orphan receipt blobs still not cleaned up (carry-forward, unchanged)

`src/app/api/members/reimbursements/[id]/route.ts:227` still carries the "orphan cleanup is deferred to inc3" comment; inc3 shipped without it and there is no further increment planned. Storage cost accumulates unbounded. Low priority, but the deferral is now permanent rather than temporary and should be re-scoped as its own backlog item rather than left as a stale comment.

### L3 — No rate limiting or lockout on credentials sign-in or password-reset request

`src/lib/auth/index.ts`'s `authorize()` and `src/app/api/auth/forgot-password/route.ts` have no attempt-count enforcement. `failed_login_attempts` (DECISION-033) is explicitly visibility-only — an admin dashboard, not a blocking control — so an attacker can make unlimited credential-stuffing attempts against any member's password, or spam a member's inbox with reset emails, with only bcrypt's inherent per-attempt cost slowing them down. Low priority for a ~44-person club portal, but worth a backlog item (e.g., a simple per-IP/per-email sliding-window check before calling `bcrypt.compare` or sending a reset email).

### L4 — `forgot-password` has a response-timing side channel that weakens its own anti-enumeration design

`src/app/api/auth/forgot-password/route.ts` correctly always returns the same success message regardless of whether the account exists — but only calls (and awaits) `sendEmail()` when it does. A response-time comparison (existing-account requests wait on an outbound Resend call; non-existent-account requests don't) leaks the same information the uniform response message is trying to hide. **Fix:** await a fixed-cost no-op (or fire-and-forget the send) on both branches so timing doesn't vary.

### L5 — Public member-photo endpoint has no gating; only used for leadership but not scoped to leadership

`src/app/api/public/members/[id]/photo/route.ts` serves any member's stored profile picture, unauthenticated, given only their UUID — with no check that the member is actually a board/leadership member (its own doc comment says "used by the About page leadership grid," but the route itself enforces nothing). Members table IDs are random UUIDs (not enumerable), which bounds the risk, but this is exactly the disclosure vector that makes **H1** concretely exploitable (see H1's exploit chain) — the public About page hands out board members' UUIDs by design, and any member whose UUID becomes known through any other legitimate UI path (admin directory, RSVP export, etc.) has their photo servable to the entire internet regardless of whether they're leadership. **Fix:** scope the query to join against the current Board group membership (mirroring `/api/public/leadership`'s own query), so the endpoint only ever serves photos for people actually on the public leadership page.

### L6 (informational) — `/api/public/leadership` appears to be dead code, duplicating `about/page.tsx`'s own leadership query

`src/app/api/public/leadership/route.ts` is not referenced by any component (`about/page.tsx` queries the DB directly instead). It also reimplements the board-position ranking logic that `src/lib/board-positions.ts`'s own doc comment already flags as a known duplicate ("`/api/public/leadership/route.ts`'s own ad hoc position lookup"). Not itself a vulnerability, but it's unnecessary public attack surface plus a second copy of logic that should be consolidated per CLAUDE.md's duplication rule — worth a small cleanup item, either delete the route or make `about/page.tsx` use it.

### L7 — Member self-serve profile-picture upload checks only a `data:image/` prefix, not magic bytes

**File:** `src/app/api/members/profile-picture/route.ts`

Inconsistent with the app's own established upload-validation standard: `admin/upload` (campaign images, see M3) at least checks a `Content-Type` allowlist, and `members/reimbursements/upload` does real magic-byte validation. This route accepts anything whose data-URL prefix claims to be `image/*`, unchecked further. A member could set a crafted `data:image/svg+xml` payload as their own profile picture. Actual exploit risk is low — it renders via a plain `<img src>` in the member directory, and browsers don't execute embedded SVG script when loaded that way — but it's the same content-type-confusion primitive as M3, one tier down in privilege (self-service member, not `CAMPAIGNS_MANAGE` admin). **Fix:** reuse the same magic-byte validator the reimbursement-upload path already has, and restrict to jpeg/png/webp/gif like `admin/upload`.

### L8 (informational) — `db.select().from(members)` with no explicit column list in `admin/members/route.ts`

**File:** `src/app/api/admin/members/route.ts:38`

Returns every column on the `members` table, correctly gated behind `MEMBERS_VIEW` today so not exploitable now — but any sensitive column added to `members` in the future (an internal note field, say) would silently start flowing through this endpoint with no additional review trigger. Not a finding requiring action this cycle; noted so a future schema change to `members` gets a matching look at this route's response shape.

## Confirmed Closed Since Last Cycle

- **SSRF in `zeffy-meta`** (2026-06-24 `FINDING-B`) — now enforces a strict hostname allowlist (`zeffy.com`/`www.zeffy.com`, `https:` only) on the parsed `URL` object, with an explicit code comment explaining why a substring check would have been bypassable. Closed.
- **`cleanupExpiredTokens` `eq()` bug** (2026-06-24) — now correctly uses `lte()`. Closed.
- **8 admin list pages missing page-level gates** (`FINDING-A`, 2026-05-27/2026-06-24) — closed for the top-level `page.tsx` files, and now enforced by `admin-page-feature-gates.test.ts`. (Superseded by H1 above, which found the same defect class one route level deeper, outside that test's current reach.)
- **Password-reset token handling** — 32-byte CSF-random token, SHA-256 hashed at rest, 24h expiry, single-use (deleted on redemption), prior tokens invalidated on a new request, opportunistic pruning. No issues found.
- **SQL injection surface** — every `sql\`...\`` usage found (members/users lookups, newsletter, leadership, ledger filings copy) uses Drizzle's parameterized tagged-template interpolation; no string concatenation into raw SQL anywhere in `src/`.
- **`dangerouslySetInnerHTML`** — every usage is either `JSON.stringify()`'d JSON-LD (safe) or the one documented, admin-authored welcome-packet exception; the email-queue viewer deliberately uses a sandboxed iframe instead. No undocumented raw-HTML rendering.
- **Google Group sync** — all 6 group-sync route handlers (`groups/[id]/sync`, `sync-board-role`, `members/sync-club`, `groups/[id]` GET/PUT/DELETE, `groups/[id]/members`) correctly gate on `GROUPS_MANAGE`/`MEMBERS_EDIT`; no credential (`GOOGLE_GROUPS_REFRESH_TOKEN`, admin subject) ever logged or returned to the client — only Google's own error messages surface, and those land in `googleGroupSyncError` or the server console, not a client response body. Group membership diffs are always computed from the portal DB, never from attacker-supplied emails/group IDs, so there's no authorization-boundary issue letting a caller target an arbitrary Google Group. Board-role auto-sync writes every grant/revoke to `permissionAuditLog`. Domain-wide-delegation impersonation via `GOOGLE_ADMIN_EMAIL` is unchanged from prior cycles. OAuth scopes themselves are granted out-of-band via Workspace domain-wide delegation and aren't visible in code — recommend confirming in the Workspace admin console that the authorized scope list is narrowly `admin.directory.group`/`admin.directory.group.member`, not broader.
- **NextAuth session shape** — the session callback (`src/lib/auth/index.ts`) exposes only `id/role/roles/features/memberId/isActive` to the client; no raw Google access/refresh tokens land in the session. Google sign-in requests only NextAuth's default `openid email profile` scopes, nothing broader.
- **Member/proposal/reimbursement ownership checks** — every `/api/members/*` route with an `[id]` param verifies `submittedByMemberId`/`proposerUserId` against the session before returning or mutating (404-not-403 pattern for proposals is a nice touch against ID-existence probing).
- **Registration** — Turnstile-gated, requires a matching active member record, rejects duplicate accounts. Bounded account-enumeration side channel via error message differences is an accepted, intentional design tradeoff (registration must explain why it failed), not flagged as a finding.
