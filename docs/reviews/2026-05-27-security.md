# Security Review — 2026-05-27

**Outcome:** 0 critical, 4 high, 3 medium, 3 low; immediate action needed on Next.js + drizzle-orm upgrades and two missing auth gates.

**Reviewers:** api-developer (application/auth/route-handler half) + database-admin perspective (schema/data half)

---

## Checked and Clean

- All admin routes under `src/app/api/admin/**` call `auth()` before any DB work — no unauthenticated access path found (with two exceptions noted below).
- No real secrets committed to git. `.env.local` is gitignored. `.env.example` contains only placeholder values.
- Drizzle ORM is used for all DB access. All `sql\`...\`` template literals reviewed below — none interpolate raw user input unsafely.
- Password reset token is SHA-256 hashed in the database; the raw token is only in the email link. 24-hour expiry and single-use deletion are both implemented. Anti-enumeration response on the forgot-password endpoint is correct.
- `bcryptjs` work factor is 10 on all `bcrypt.hash()` calls — acceptable.
- Turnstile is validated server-side (not just client-side) on: contact form, newsletter subscribe, membership application, and account registration. All four call `verifyTurnstile()` before touching the database.
- Email HTML in the contact form, suggestions endpoint, and JWT new-user notification all use an `esc()` helper that encodes `& < > "`. No unescaped user input reaches an HTML email sink in any of those paths.
- Google Group sync (`syncGoogleGroup`, `syncClubMembersList`) uses server-only credentials stored in env vars. The sync is never triggered by unauthenticated callers — all trigger paths require auth + a feature check.
- `allowDangerousEmailAccountLinking: true` on the Google provider is intentional (org accounts linking to existing password accounts) and documented behavior. Acceptable given that all OAuth sign-ins still pass through the `signIn` callback which blocks deactivated accounts.
- Anonymous RSVP at `/api/events/[id]/rsvp` requires `name` + `email` from the request body; the response returns the persisted row but does not expose other members' PII. The public event signup list endpoint (`/api/events/[id]/signup`) was not found as a separate public read endpoint — the write path is authenticated.
- `src/app/api/public/leadership/route.ts` returns only `firstName`, `lastName`, and `position` — no email, phone, or address fields.
- `src/app/api/public/members/[id]/photo/route.ts` returns only the stored profile image bytes — no PII.
- SQL injection surface: all `sql\`...\`` template literals reviewed. All user-supplied values are passed as Drizzle parameterized arguments (the `${value}` placeholder outside the raw SQL string). Literal SQL strings (`'board of directors'`, `NOW()`) contain no user input. No injection risk found.
- Profile picture upload (`/api/admin/members/[id]/profile-picture`) accepts only a data URI with a 400 KB length cap and validates the `data:image/` prefix. No disk write.
- OAuth tokens (Google access/refresh tokens) are stored by the DrizzleAdapter in the `accounts` table. Only the server can read them. They are never forwarded to the client via the session callback — only `id`, `role`, `roles`, `features`, `memberId`, and `isActive` reach the JWT/session.
- The release-notes endpoint (`/api/admin/release-notes`) validates that the `file` query param matches `/^v[\d.]+\.md$/` before constructing the file path, preventing path traversal.
- The campaign image upload endpoint (`/api/admin/upload`) uses `randomUUID()` for the filename and only writes to `public/uploads/campaigns/`. The original filename from the client is used only to extract the extension via `.pop()`, and the extension is not validated against a strict allowlist — but the MIME type is checked against `ALLOWED_TYPES` before the extension is used. Low residual risk.

### FINDING-2 (High) — drizzle-orm 0.45.1 has a SQL injection CVE; upgrade to 0.45.2

**Location:** `package.json` — `"drizzle-orm": "^0.45.1"` (resolved to 0.45.1 per lockfile)

**What's wrong:** GHSA-gpj5-g38j-94v9 — "Drizzle ORM has SQL injection via improperly escaped SQL identifiers." The CVE affects versions `<0.45.2`. The installed version is 0.45.1.

**Exploit/impact:** The advisory involves improperly escaped identifiers in certain Drizzle query builder paths. While this codebase uses straightforward parameterized queries for all user input, upgrading is required to close the vulnerability regardless of usage patterns.

**Suggested fix:** `pnpm add drizzle-orm@latest` or pin to `>=0.45.2`.

### FINDING-3 (High) — `xlsx` has Prototype Pollution and ReDoS CVEs with no available patch

**Location:** `package.json` — `"xlsx"` (exact version in lockfile)

**What's wrong:** Two CVEs:
- GHSA-4r6h-8v6p-xvw6 — Prototype Pollution in SheetJS (`<0.19.3`); `Patched versions: <0.0.0` — meaning no npm patch exists.
- GHSA-5pgg-2g8v-p4x9 — ReDoS in SheetJS (`<0.20.2`); same situation — no published patch on npm.

The SheetJS project moved to a commercial model; the patched versions are not published to the npm registry.

**Exploit/impact:** `xlsx` is used in two admin-only export endpoints:
- `GET /api/admin/members/export` — exports active member data to XLSX
- `GET /api/admin/newsletter/export` — exports newsletter subscribers to XLSX

Both endpoints are gated behind `auth()`. The members export additionally checks only `session?.user` (not a specific feature — see FINDING-4 below). The Prototype Pollution issue could affect server memory if a maliciously crafted XLSX is ever _parsed_ (not exported), but these endpoints only _write_ XLSX, never parse uploaded XLSX files. The ReDoS risk is negligible for write-only usage. Risk is currently low in practice, but the unpatched status is a permanent concern.

**Suggested fix:** Evaluate replacing `xlsx` with `exceljs` (actively maintained, MIT, publishes CVE-free npm releases) for both export endpoints. No schema change required — the replacement would only affect `src/app/api/admin/members/export/route.ts` and `src/app/api/admin/newsletter/export/route.ts`.

### FINDING-4 (Medium) — Two data-export endpoints require only authentication, not a specific feature

**Locations:**
- `src/app/api/admin/members/export/route.ts:57` — `if (!session?.user)` — no `hasFeature()` check
- `src/app/api/admin/newsletter/export/route.ts:10` — `if (!session?.user)` — no `hasFeature()` check

**What's wrong:** Any authenticated portal user — including a newly registered member with only the default `member` role — can call `GET /api/admin/members/export?format=zeffy` and receive an XLSX file containing the full name, email, phone, address, city, state, zip, and branch fields for every active member. Similarly for the newsletter subscriber export.

The members export returns the full `members` table row (`db.select().from(members)`), which includes all PII fields. This is the most sensitive endpoint in the application in terms of bulk PII exposure.

**Exploit/impact:** A member with no admin privileges can exfiltrate the full member roster including contact details. This is a GDPR-relevant mass-PII exposure for any member willing to call the API directly.

**Suggested fix:**
- Members export: add `const canExport = await hasFeature(session.user.id, FEATURES.REPORTS_EXPORT); if (!canExport) return NextResponse.json({ error: "Forbidden" }, { status: 403 });`
- Newsletter export: same gate — `FEATURES.REPORTS_EXPORT` or `FEATURES.MEMBERSHIP_MANAGE`, whichever is more appropriate for the intended audience.

### FINDING-5 (Medium) — Email-queue retry endpoint uses role-name string check instead of feature gate

**Location:** `src/app/api/admin/email-queue/retry/route.ts:19-21`

```typescript
if (!session.user.roles?.includes("admin") && session.user.role !== "admin") {
  return NextResponse.json({ error: "Forbidden" }, { status: 403 });
}
```

**What's wrong:** This check reads the `roles` array from the JWT session rather than calling `hasFeature()` through the server-side permission system. This is the only route handler in the codebase that uses this pattern; all others use `hasFeature()`. Two problems arise:

1. It is inconsistent with the project's permission model, making it easy to miss during future role changes.
2. The session `roles` array is populated at JWT-issue time and may be stale for up to the JWT lifetime. If a role is renamed or a user's roles are changed, this check can remain wrong until the user re-authenticates. `hasFeature()` via `permissions-server.ts` has a 60-second cache which is much fresher.

**Exploit/impact:** Low in practice — the check does require an `admin` role — but the inconsistency is a maintenance hazard.

**Suggested fix:** Replace the role-name check with `hasFeature(session.user.id, FEATURES.ADMIN_USERS)` (or a new `FEATURES.EMAIL_QUEUE_MANAGE` if finer control is desired) using `permissions-server.ts`, consistent with all other admin endpoints.

### FINDING-6 (Medium) — JWT auto-link fires on every sign-in before member link is confirmed; silently writes DB rows outside of the JWT callback's normal return path

**Location:** `src/lib/auth/index.ts:106-131` (auto-link block) and `:136-155` (unlinked-user alert block)

**What's wrong:** The JWT callback contains two fire-and-forget `db.update()`/`db.query()` chains (lines 107 and 136) that run outside the awaited body of `jwt()`. They are chained `.then(...).catch(() => {})` but have no timeout. In a high-latency or overloaded DB scenario these chains will still attempt to run after `jwt()` has returned. Additionally, the unlinked-user email notification fires on every sign-in by any user who does not yet have a `memberId` — this includes all newly registered users before an admin links them. If a user signs in repeatedly before an admin links their account, the admin inbox receives a notification on every sign-in, not just the first.

**Exploit/impact:** No direct security exploit, but the unlinked-user email sends the user's name and email to `info@westervillelions.org` on every sign-in. If a bad actor creates many accounts with addresses that match active member names, they can flood the admin inbox with notification emails. Low severity as CAPTCHA is required at registration.

**Suggested fix:** Add a guard to the notification path: only send the email on the _first_ sign-in (e.g., check `users.lastLoginAt IS NULL` before sending, or store a `notifiedAt` flag). Consider moving the auto-link DB write to the `signIn` event, where it can be `await`-ed without blocking the JWT callback.

### FINDING-7 (Low) — `allowDangerousEmailAccountLinking: true` on Google provider is not documented in code

**Location:** `src/lib/auth/index.ts:24`

**What's wrong:** The flag is set correctly and intentionally, but there is no inline comment explaining why. This flag allows a Google OAuth sign-in to take over an existing password-auth account with the same email address. Without documentation, a future maintainer may remove it not knowing it is required for the westervillelions.org org accounts to work correctly, or conversely may not know what risks to weigh if the domain configuration changes.

**Suggested fix:** Add a one-line comment: `// Required: org accounts (first-party Google sign-in) must be able to link to existing password accounts with the same email.`

### FINDING-8 (Low) — No input length limits on membership application fields

**Location:** `src/app/api/membership-applications/route.ts:43-79`

**What's wrong:** The membership application endpoint validates that `firstName`, `lastName`, and `email` are present and that Turnstile passes, but applies no length limits on any of the 18 fields it accepts. Fields like `spouseName`, `occupation`, `address`, `sponsorName`, `previousClubName` are written directly to the database without length checking. The schema column types (likely `text`) will accept arbitrary length, so an attacker who bypasses Turnstile could store very large strings.

**Exploit/impact:** Low in practice given Turnstile is enforced, but if the Turnstile secret is ever unset (which falls back to the permissive test key `1x0000000000000000000000000000000AA`), this becomes an unbounded text injection into the database.

**Suggested fix:** Add a maximum length check (e.g., 255 characters) for each string field before the DB insert. Also ensure `TURNSTILE_SECRET_KEY` is always set in production.

### FINDING-9 (Low) — Turnstile fallback to test key in production if env var is unset

**Location:** `src/app/api/contact/route.ts:7`, `src/app/api/newsletter/subscribe/route.ts:7`, `src/app/api/membership-applications/route.ts:6`, `src/app/api/auth/register/route.ts:9`

**What's wrong:** All four public form endpoints fall back to `"1x0000000000000000000000000000000AA"` — Cloudflare's always-pass test secret — when `TURNSTILE_SECRET_KEY` is not set. This is correct for local development but if the variable is accidentally omitted from the production environment, all four endpoints accept any Turnstile token (including none submitted via direct API calls).

**Exploit/impact:** Would allow spamming the contact table, newsletter subscriptions, and membership applications, and would allow account registration by anyone regardless of bot protection.

**Suggested fix:** Log a startup warning if `TURNSTILE_SECRET_KEY` is not set and the process is running in a production-like environment (e.g., `NODE_ENV === "production"`). This is a monitoring/ops hardening item rather than a code defect, since the test key is intentional for dev.

## OAuth and Session Token Storage

- Google OAuth access tokens and refresh tokens are stored in the `accounts` table by the DrizzleAdapter. This is the standard NextAuth.js storage model.
- The session uses JWT strategy (`session: { strategy: "jwt" }`). The JWT is stored as an `httpOnly` cookie, never readable by client-side JavaScript.
- The JWT payload exposed to the client through the `session` callback contains: `id`, `role`, `roles`, `features`, `memberId`, `isActive`. No tokens, passwords, or raw PII land in the session/JWT.
- The Google Groups OAuth client uses a `refresh_token` stored in `GOOGLE_GROUPS_REFRESH_TOKEN` (env var, not committed). The `subject` impersonation is set via `(auth as any).subject`, which is the correct pattern for Google Workspace domain-wide delegation.

## Schema / Row-Level (Database-Admin Perspective)

- No raw SQL is constructed using user-supplied table or column names.
- All FK relationships use `onDelete` constraints (reviewed in schema.ts).
- The `email_queue` table stores full email HTML. Admin-level access is required to view/retry entries. The HTML stored in the queue includes the unlinked-user notification which contains the signing-in user's name and email — acceptable, as this is in a server-only table.
- Password hashes are stored in `users.password`. The column is not `SELECT`-projected in any public-facing endpoint response.
- `users.memberId` FK allows multiple users to reference the same member record (no unique constraint per the comment in the link-member endpoint). This is intentional per the codebase design.
