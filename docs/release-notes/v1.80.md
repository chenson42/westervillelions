## 1.80.0 — 2026-09-25

### Defect Fix: Email could fail silently and be recorded as sent

**Problem:** Between **2026-08-28 and 2026-09-25**, roughly 34 emails the club believed it had
sent were never delivered — proposal notifications, dues reminders, contact-form replies, donor
acknowledgments and reimbursement requests among them. Nothing anywhere indicated a problem. The
admin email queue showed every one of them as **Sent**.

**Root Cause:** Two independent faults, and the second one hid the first.

- The club's Resend API key was revoked at the end of August. Every send after that was rejected.
- The application never noticed. Resend's library **returns** an error rather than raising one,
  and the code discarded that return value before writing "sent" to the queue. A rejected send was
  therefore indistinguishable from a successful one. A separate branch meant to help local
  development did the same thing whenever no API key was configured at all.

The result was an outage that produced no failures, no retries and no warnings — for four weeks.

**Fix:**
- A send that cannot happen in production is now recorded as **failed**, with the reason attached,
  and is never reported as sent.
- The **retry** path now inspects the result it gets back from the email provider, so a rejected
  retry is recorded as a failure rather than a success.
- The admin sidebar shows a **count of failed emails** beside "Email Queue", so a problem is
  visible from anywhere in the admin area instead of only on a page nobody had reason to open.
  Nothing is shown when there are no failures.

### Feature: Retry a failed email one message at a time

**Value:** Recovering from the outage above meant choosing carefully. Some messages needed
resending; others did not — an expired password-reset link is useless, and a donor who has already
been thanked should not receive a second receipt. The existing control could only retry everything
at once.

#### What's New

- A **Retry** button on each row of the Failed Emails table, so individual messages can be resent
  and others left alone.
- A confirmation step naming the **exact recipient and subject** before anything is sent, because
  this is real mail to a real person and cannot be recalled.
- Per-message results: retry several and you are told precisely which succeeded and which did not,
  with the actual error.
- A message already being retried cannot be sent twice, even if the button is clicked repeatedly or
  by two people at once.
- The existing "retry everything" control is unchanged and still cannot resend messages that were
  not already scheduled for a retry.

### Security: The non-production email block now covers the retry path

**Background:** Outbound email is refused outside production unless the recipient is explicitly
allowed, because two separate test runs once delivered real mail to the club — a 44-person mailing
list, and later 16 board members who received a fake $500 approval request.

The retry path contacted the email provider directly and never consulted that block. No mail
escaped through it, but adding a one-click Retry button would have made the gap easy to reach.

**Changes:**
- The rule now lives in one place and both the normal send path and the retry path use it, so they
  cannot drift apart.
- A retry blocked outside production is recorded as blocked and counted as neither sent nor failed.

#### Known Limitations

- If the server is killed at the exact moment a retry is claimed — a deploy or a timeout landing
  mid-request — that message can be left in a state where it no longer appears anywhere. Rare, and
  strictly safer than the duplicate-send problem it replaced; tracked as backlog item **B-66**.
- The unchecked-result fault described above has been corrected on the retry path but **not yet on
  the main send path**; tracked as **B-65**.
