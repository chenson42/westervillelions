## 1.12.1 — 2026-05-18

### Infrastructure: Adopt formal development pipeline and test infrastructure

**Background:** As the codebase grows, ad-hoc "build a thing, push it, hope" stops scaling. This change brings in a formal six-phase development pipeline (analyst → architect → tech-lead → implementer → qa → analyst sign-off) borrowed from the user's `claudecode` starter project, the corresponding cadence-based periodic reviews, and the actual test infrastructure (Vitest + Playwright) that the pipeline assumes. None of this changes user-facing behavior — it's a tooling and process upgrade for everything that ships next.

**Changes:**

- **2 new agents.** `analyst` owns Phase 1 (functional refinement before design) and Phase 6 (shipped-vs-intent sign-off after QA). `qa` owns Phase 5 (test verification). Both adapted for this project — qa expects Vitest + Playwright, analyst recognizes this project's four user surfaces (anonymous visitor, signed-in member with no usable role, signed-in member, admin).
- **All 7 existing agents refreshed** (`api-developer`, `architect`, `database-admin`, `deployment-engineer`, `full-stack-developer`, `tech-lead`, `ux-developer`) — pulled the newer claudecode shape and stripped every starter-only reference (TOTP, `audit_events`, `feature_flags`, deck rendering, `src/proxy.ts`, `npm`/`npm run`), preserving the Lions Club's `FEATURES`/`hasFeature()` permission system, `lions-blue`/`lions-gold`/`rounded-2xl` UX conventions, and `ConfirmDialog` rules.
- **All 5 skills refreshed.** `pre-push` now runs `pnpm test` (Vitest) and `pnpm test:e2e` (Playwright) in addition to typecheck + build, with a "skip with note" fallback when the test runner isn't installed yet so the skill doesn't break partial-rollouts.
- **CLAUDE.md grows by 6 sections** (TOC, Agent Roster, Development Pipeline, Periodic Reviews, Document Naming, Workflow Rules, Key Invariants) while every existing Lions Club section (Project Overview, Brand Guidelines, Technology Stack, Project Structure, Key Features, Integrations, Database Schema Patterns, Database Migrations, Key Patterns, UX Guidelines, Content Guidelines, Gotchas) is preserved.
- **Periodic reviews framework.** Seven rolling reviews (test coverage 7d, retrospective 7d, code 30d, documentation 30d, security 30d, agent-instruction 30d, dependencies 30d) with a cadence check at session start against `docs/reviews/log.md`.
- **Test infrastructure installed.** `vitest.config.ts`, `playwright.config.ts` (chromium-only), new dev dependencies (`vitest`, `@vitest/coverage-v8`, `@playwright/test`, `vite-tsconfig-paths`), `pnpm test` / `pnpm test:watch` / `pnpm test:e2e` scripts, `.gitignore` updated for `test-results/`, `playwright-report/`, `.last-run.json`.
- **First tests landed.** `src/lib/events.test.ts` covers `getNextOccurrence` and `formatRecurrence` with 9 tests — including a regression test for the v1.11.6 past-events misclassification (a recurring series whose `recurrenceEndDate` has passed correctly returns null). `e2e/smoke.spec.ts` covers public-site smoke: homepage renders, events page renders, unauthenticated `/members` redirects to signin/access-pending. 9/9 unit + 3/3 e2e passing.

## 1.12.0 — 2026-05-18

### Feature: Member user auto-provisioning

**Value:** Every member needs a `users` row to RSVP to events, be assigned to groups, and log into the member portal. Until now, `POST /api/admin/members` (the admin "Add Member" form) created a member row but never created the corresponding user account — leaving the member invisible to the rest of the system. The discovery case was a recently-added member who couldn't be RSVP'd to a Farmer's Market occurrence and had to be patched up by hand. The membership-application approval flow already did the right thing, so this release extracts that logic into a shared helper and wires it into every member-creation path so the gap is impossible going forward.

#### What's New

- **Email is required on every member and unique (case-insensitive).** The Add/Edit Member forms enforce it visually with an asterisk and inline 409 error; the API returns `400 "Email is required"` or `409 "A member with this email already exists"` on violation. Pre-flight DB survey confirmed 0 rows missing email and 0 case-insensitive duplicates, so the new constraints applied cleanly with no backfill.
- **Direct admin member creation now provisions a user account.** Creating a member via the Add Member form now:
  - Looks up any existing `users` row by case-insensitive email and either links it to the new member, or creates a fresh `users` row (role `member`, `is_active: true`, linked via `users.member_id`).
  - Generates a 24-hour SHA-256-hashed password-reset token so the new member can set a password.
  - Queues a welcome email to the member's address with the password-set link plus a note explaining that Google sign-in with that same email also works.
  - Returns `{ userLinked: 'created' | 'existing' }` on the response so the UI knows which path was taken.
- **Editing a member's email propagates the change to the linked `users.email`** so the member's existing login keeps working. NextAuth `accounts` rows (Google OAuth) are intentionally untouched — Google's `providerAccountId` is a stable Google account ID, not the email, so OAuth sign-in continues to work without re-linking. The PATCH route also defensively provisions a user account if it encounters a legacy member without one.
- **Approval flow refactored to use the same helper.** Behavior is byte-identical to before; the inlined 55-line provisioning block is replaced with a single `provisionUserForMember(...)` call. One shared code path means one place to fix in the future.
- **Welcome email rewritten to be flow-neutral.** Previously the body said "your application has been approved" — that's no longer true for direct-admin-created members. The new body welcomes them to the member portal, presents the password-set link, and mentions that sign-in with the matching Google account is an alternative.

- `src/lib/members.ts` — `provisionUserForMember()` shared helper plus the rewritten `sendWelcomeEmail`
