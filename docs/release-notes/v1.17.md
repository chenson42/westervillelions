## 1.17.1 — 2026-05-22

### Defect Fix: Write-In Attendee Names Now Visible to Members

**Problem:** After v1.17.0 shipped admin-recorded write-in (guest) signups, the public event detail page started showing inflated attendance counts without the matching names. On the Farmers Market series, members saw "33 attending" on an occurrence but the visible signup list was nearly empty — every admin-recorded guest counted toward the total but never appeared in the badge list. Members lost the ability to see who was actually signed up for an event.

**Root Cause:** The public event detail page joined RSVP rows to the `users` table and only displayed names from `users.name`. Write-in rows have no `user_id` — the attendee's name lives in `event_rsvps.rsvp_name`, which the page query never read. The count loop already summed every non-declined RSVP, so counts and badges drifted apart.

**Fix:** The page query now also reads `event_rsvps.rsvp_name` and falls back to it when the row has no linked user. Both members and admin-recorded guests now appear in the per-occurrence signup badges; counts and visible names match.

**Testing:**

- [x] Manually verified on the Farmers Market series: counts and per-occurrence signee badges now match.
- [x] Vitest unit suite (115/115) and typecheck/production build all pass.

## 1.17.0 — 2026-05-20

This release bundles a new admin feature with a defect fix to the signup-count display. Both touch the same admin surfaces and ship together.

### Feature: Write-in (Guest) Signups for Admins

**Value:** Events frequently have attendees who don't have member accounts yet — prospective members, walk-ups at the Farmers Market booth, guests of members. Until now, admins had no way to add those people to an event's attendee list without first creating a full user record. Write-ins let admins record an attending guest by name (and optionally an email) in one step, taking a capacity slot just like a member RSVP. The guest is visually distinguished with a "Guest" badge so it's never confused with a member.

#### What's New

- **Write-in form** below the existing "Add Member" control on every admin event detail page — both per-occurrence (recurring events) and event-level (non-recurring events with RSVPs enabled).
- **Fields:** name (required) + email (optional). Walk-ups with no contact info are valid.
- **Guest badge** on every written-in row so admins can tell at a glance who is a member and who isn't.
- **Inline edit:** click a guest's name to update it (or add an email later when you get one). Members cannot be renamed through this path.
- **Remove with confirmation** via the standard `<ConfirmDialog>`.
- **Capacity over-ride:** when an occurrence is full, the form shows an inline yellow warning ("This occurrence is at capacity — adding this guest will exceed the limit") but allows the admin to proceed. The per-occurrence count chip turns amber to flag the overage.
- **Email-match notice:** if the typed email matches an existing member, the form surfaces a yellow notice with two CTAs — "Add as Member" (routes through the existing member-add flow) and "Continue as Guest." Educates the admin without forcing a choice.
- **Audit trail:** every write-in records the admin who created it via a new nullable `created_by_user_id` column on `event_rsvps`.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `events.edit` (existing) | Adding, editing, or removing a write-in. No new permission key. |

#### New Routes

- `GET /api/admin/members/lookup?email=...` — Returns `{ id, name, email }` for an admin-typed email if it belongs to a member, otherwise `null`. Used by the email-match notice.
- `PATCH /api/admin/events/[id]/signup/[rsvpId]` — Inline edit for a guest row. Refuses to modify member rows.

The existing `POST` and `DELETE` on `/api/admin/events/[id]/signup` were extended with a discriminated body so admins can post a `kind: "guest"` row or delete a specific row by `{ rsvpId }`.

#### Schema Change

A new nullable `event_rsvps.created_by_user_id` column was added (audit trail for admin-created write-ins). Migration `0038_event_rsvps_created_by.sql` is idempotent and safe to re-run.

### Defect Fix: Recurring Event Signups Roll Up Across All Occurrences

**Problem:** On the admin events list, a recurring event like the Farmers Market series displayed only the signups for the next upcoming occurrence (e.g., "2 signups") even though members had signed up across many dates. On the admin event detail page, recurring events showed no series-level signup total at all — only the per-occurrence breakdown.

**Root Cause:** The list page intentionally scoped each recurring event's count to a single target date computed from `getNextOccurrence`. RSVPs on every other occurrence were silently filtered out. The detail page computed the cross-occurrence totals but only rendered them in the non-recurring branch of the JSX, so recurring events never saw the headline numbers.

**Fix:**

- The admin events list now sums RSVPs across **all** occurrences of a recurring event, excluding any whose date is in the cancelled-occurrence set. Non-recurring events are unaffected.
- The admin event detail page now renders a "**X attending across Y occurrences**" header above the per-occurrence breakdown for recurring events, with optional secondary line "Z maybe · W declined." When every occurrence in the series is cancelled, the header reads "All occurrences cancelled."
- Cancelled occurrences are excluded from both the count and the occurrence total on both surfaces.

**Testing:**

- [x] Four Playwright e2e tests in `e2e/recurring-signup-rollup.spec.ts` guard the regression: list rollup sum, cancelled-occurrence exclusion, detail header presence on recurring events, detail header absence on non-recurring events.
- [x] Seven Playwright e2e tests in `e2e/write-in-signups.spec.ts` guard the write-in flow: add to recurring, add to non-recurring (conditionally skipped when no eligible event), inline edit, remove with confirmation, capacity over-ride, email-match notice, cancelled-occurrence form suppression.
- [x] Manually verified both flows on the Farmer's Market series in dev.
