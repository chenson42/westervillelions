## 1.55.0 — 2026-08-05

### Feature: Budget "Notes & Assumptions" render as Markdown

**Value:** The budget's Notes & Assumptions block is the treasurer's explanation to the board — why a
line moved, what a committee recommended, which questions are still open. As a single wall of
preformatted text, a page of that reads as undifferentiated prose exactly when a board member is
skimming for the one paragraph that concerns them. Markdown gives the treasurer headings, emphasis,
and lists, so a long note stays scannable both on screen and on the printed board packet.

#### What's New

- Notes & Assumptions render Markdown — headings, bold and italic, bulleted and numbered lists,
  links, blockquotes, and GFM tables — in both the on-screen budget view and the printable
  board-ready worksheet.
- The editor still edits raw Markdown source, with an unobtrusive "Markdown supported" hint beside
  the character counter. The 4,000-character limit is unchanged.
- Notes written before this release are unaffected: blank-line-separated paragraphs still render as
  separate paragraphs, so nothing that already existed reads differently.
- Raw HTML is deliberately not supported — Markdown only.

### Defect Fix: Budget-committee members were locked out of the entire admin area

**Problem:** A member given a budget-committee role — carrying `budget.view` and `budget.edit`, the
permissions that exist precisely so a non-officer can review the draft budget — saw no "Admin" link
in the header, and a direct link to the budgeting page bounced them to `/access-pending`. The
permission grant was correct and the budgeting page's own gate would have admitted them; they simply
could not get to it. Reported by a budget-committee member who could not open the budget she had been
asked to review.

**Root Cause:** `admin.dashboard` was being used as a proxy for "has some admin-area access." The
admin layout wraps every admin route and admitted only Admins and `admin.dashboard` holders, so it
rejected the user before any page-level or sidebar-level check ran. The header's Admin link carried
the same hardcoded check. The sidebar already handled budget permissions correctly — it was never
reached.

**Fix:** Admission to the admin area is now derived from the same navigation data the sidebar renders
from, via a shared `canAccessAdminArea()` helper: hold any feature that exposes a section, and you
can reach that section. Because both the gate and the sidebar now read one source, a future
permission can't be added to one and forgotten in the other. The `/admin` dashboard itself keeps
requiring `admin.dashboard` and redirects other admitted users to their first accessible section, so
opening up the shell does not expose org-wide statistics. No role bindings were widened —
budget-committee still does not hold `admin.dashboard`.

**Testing:**
- [x] Unit coverage for `canAccessAdminArea` and `getFirstAccessibleAdminHref`, including a
      regression case pinned to the reporting member's exact feature set, plus admin-holder,
      no-admin-feature, and empty/null/undefined cases.
- [x] Full suite green (895 tests), typecheck clean, production build succeeds.

### Security: brace-expansion advisory GHSA-rgw5-rvv9-x895

**Background:** A new high-severity advisory supersedes the mitigation this project already carried:
the existing override pinned `brace-expansion` to `>=5.0.8`, but the DoS bypass is only patched in
`5.0.9`. The package reaches the tree transitively through `exceljs → archiver → glob → minimatch`,
used by the members and newsletter export routes.

**Changes:**
- Override bumped to `>=5.0.9` — a patch bump within the major already in use.
- `pnpm audit --prod --audit-level=high` returns clean; test suite and production build re-verified
  after the dependency change.

### Infrastructure: one-off ledger scripts can target production explicitly

**Background:** The ledger maintenance scripts under `scripts/` resolved their target from
`DATABASE_URL` only, so operating on production data meant editing environment files by hand.

**Changes:**
- Scripts now resolve `PROD_DATABASE_URL` first, falling back to `DATABASE_URL`/`DB_URL`, and print
  a loud `*** TARGET: PRODUCTION ***` banner whenever they are pointed at production. All remain
  dry-run until `--apply` is passed.
- Note for operators: with `PROD_DATABASE_URL` set in the environment, these scripts default to
  production rather than dev. The banner and the dry-run default are the safeguards.
