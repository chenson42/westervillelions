## 1.11.6 — 2026-05-18

### Enhancement: Past events archive on the member portal

**Value:** Members often want to revisit a past event — most commonly to look at a signup sheet for a recurring activity that has already started its season. The Past Events list on `/members/events` was rendered as inert text, sorted oldest-first, and grew unbounded as the club's history accumulated. There was no way to click through to an event's detail page from this list. On top of that, recurring series like the Farmer's Market Signup were jumping to "Past" the moment their first occurrence passed — so a series that runs May → September was disappearing from the Upcoming section in mid-May.

**Changes:**
- Past Events list on `/members/events` now shows only events from the last 6 months, sorted **newest first**, with each card a clickable link to `/events/[id]`
- New "See more past events" link appears when older history exists, leading to a full archive page at `/members/events/past`
- Upcoming/Past classification now uses `getNextOccurrence` (the same logic the public events page uses): a recurring series stays in Upcoming as long as it has a future occurrence within its recurrence window, and only moves to Past once the whole series has ended
- Past event date display now uses the series' effective end date (recurrence end for recurring events, start date for one-time events) — more meaningful than always showing the original start date for a multi-month series

## 1.11.5 — 2026-05-13

### Defect Fix: Whitespace gap on the Plastic Film Recycling card

**Problem:** After v1.11.4 grew the eyeglass drop-off list from 10 to 16 sites (with phones), the Eyeglass Donation card on `/programs` became noticeably taller. The two-column grid stretched the Plastic Film Recycling card to match, and that card's `mt-auto` on its Drop-off Location box pushed the embedded map all the way to the bottom — opening a large empty band between "What we cannot accept" and the map.

**Fix:** Removed `mt-auto` from the Plastic Film card's drop-off location wrapper so the map sits directly below the lists. Any leftover vertical space now lands at the bottom of the card rather than in the middle.

## 1.11.3 — 2026-05-08

### Defect Fix: Users created via Google OAuth had no role; admin events row over-counted RSVPs for recurring events

**Problem:**
- 35 user accounts existed in the database with zero rows in `user_roles`. They had been created by the NextAuth `DrizzleAdapter` on first Google sign-in, which inserts the `users` row but never touches `user_roles`. The three explicit code paths (`/api/auth/register`, `/api/admin/users`, membership-application approval) already assign the `member` role correctly — only the OAuth path was leaking.
- On `/admin/events`, the recurring "Farmer's Market Signup" event displayed "9 attending" even though no one had signed up for the next occurrence yet. The admin events page aggregated RSVPs by `event_id` only, summing every future occurrence of a recurring series into a single row.

**Root Cause:**
- NextAuth's adapter has no concept of the app's role system, so OAuth-created users skip role assignment entirely.
- The RSVP aggregate query in `src/app/(dashboard)/admin/events/page.tsx` grouped by `(event_id, status)` and ignored `occurrence_date`.

**Fix:**
- Idempotent backfill migration assigns the `member` role to any user with no `user_roles` rows.
- Added an `events.createUser` hook in NextAuth config that assigns the `member` role for every newly created user (with an existence check, since `user_roles` has no unique constraint on `(user_id, role_id)`).
- Admin events page now computes the next upcoming occurrence per event via `getNextOccurrence(...)` and filters the RSVP aggregate to rows whose `occurrence_date` matches that date. Non-recurring events and ended series fall back to all-time totals.

## 1.11.2 — 2026-05-08

### Enhancement: Show members on the Groups index

**Value:** The member portal's `/members/groups` index previously showed only group name, description, and email — to see who was in a group, you had to click into each one. Now each card displays an avatar stack (up to 5 members, with a "+N" chip for overflow) and a "N members" link, so members can scan the directory at a glance.

**Changes:**
- Each group card now renders a member avatar pile with initials fallback for members without a profile picture.
- Avatar tooltips show the member's name and position.
- Added a "N member(s)" link beside the stack that jumps to the group detail page.
- Empty groups show a muted "No members yet" line in the same slot.
- Page issues two queries in parallel (groups + memberships joined to members) and groups them in memory by `groupId`.

<a name="1111"></a>
## 1.11.1 — 2026-05-08

### Defect Fix: Google Group sync for newly-created committees

**Problem:** Clicking **Sync Now** on a brand-new committee group failed two ways: (1) if the admin had typed an email prefix but not yet clicked **Save Changes**, sync ran against the un-saved value and failed with "No email prefix configured"; (2) after manually saving and retrying, sync errored with `Resource Not Found: groupKey`. Successful syncs also always toasted "already up to date" regardless of what changed.

**Root Cause:**
- `handleSync` in the group form only invoked `/sync` — it never persisted pending form edits first, so a freshly-typed `emailPrefix` lived only in component state.
- After `groups.insert` creates a new Google Group, Google Workspace doesn't make it queryable by `groupKey` for several seconds. The next call (`members.list`) hit a 404 propagation race and bubbled up as the outer sync error.
- The sync route returned `{ success: true }` only — it never forwarded `added`/`removed`/`failed` from the sync result, so the form's success toast logic always saw zero changes.

**Fix:**
- Form auto-saves via `PUT /api/admin/groups/[id]` before calling `/sync`.
- `syncGoogleGroup` skips `members.list` entirely when it just created the Google Group (an empty new group needs no listing) and wraps subsequent member operations and the settings patch in a `retryOnNotFound` helper that retries up to 4× with 2s backoff on HTTP 404.
- Sync route now passes `added`, `removed`, `failed` arrays through to the client so the toast reflects actual changes.

## 1.11.0 — 2026-05-08

### Feature: Custom RSVP Question + RSVP UX Overhaul

**Value:** Events can now ask attendees one optional question at RSVP/signup time (e.g. "What dish are you bringing?" for potlucks, "T-shirt size?" for service events). The RSVP form on the public event page is also clearer — picking a status no longer instantly saves; users now click an explicit **Submit RSVP** button. Attendee totals across the public and admin views finally include guests, so a 30-spot event with 28 RSVPs and 5 guests correctly reports 33 — and rejects further signups.

#### What's New

**Custom RSVP question (per event, optional)**
- Admin event form has a new "Custom RSVP question" card: type the prompt, choose Free text or Pick-one (dropdown), optionally mark required. Dropdown takes one option per line.
- Question and answer flow through every RSVP/signup surface: authenticated RSVP form, anonymous public RSVP, single-event signup button, and the per-occurrence signup list for recurring events.
- Server validates required answers and (for select type) that the answer is one of the configured options.
- Admin RSVP tables (flat and per-occurrence) get a new column titled with the question label, showing each attendee's answer.

**Clearer RSVP submission**
- Authenticated RSVP form now has explicit submit semantics: Attending / Maybe / Decline buttons select a draft, and a prominent "Submit RSVP" button (or "Update RSVP" when something changed) saves it.
- Saved state is shown via a green "✓ You're attending" indicator next to a disabled "RSVP saved" button.
- New "Remove RSVP" link cancels a saved RSVP without using browser confirms.

**Guests counted in attendee totals**
- Public event page: per-occurrence count and single-event count now sum `1 + guestCount` per non-declined RSVP. Labels read "X attendees (incl. guests)" / "X of Y spots filled (incl. guests)".
- Admin event detail (non-recurring): the green Attending card shows the headcount with a "N members + M guests" subtitle breakdown.
- Admin event detail (recurring): each occurrence's collapsed header shows total headcount with "(incl. guests)" suffix.
- Signup cap check (`/api/events/[id]/signup`) now rejects when `total RSVPs + guests >= maxAttendees`, matching the displayed numbers.

**Form bug fix**
- Admin event form: title input and other text fields no longer flicker between controlled/uncontrolled state. `handleChange` keeps text values as strings instead of coercing `""` to `null`; the API still normalizes empty strings to null on save.
