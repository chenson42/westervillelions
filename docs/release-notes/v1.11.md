## 1.11.1 — 2026-05-08

### Defect Fix: Google Group sync for newly-created committees

**Problem:** Clicking **Sync Now** on a brand-new committee group failed two ways: (1) if the admin had typed an email prefix but not yet clicked **Save Changes**, sync ran against the un-saved value and failed with "No email prefix configured"; (2) after manually saving and retrying, sync errored with `Resource Not Found: groupKey`. Successful syncs also always toasted "already up to date" regardless of what changed.

**Root Cause:**
- `handleSync` in the group form only invoked `/sync` — it never persisted pending form edits first, so a freshly-typed `emailPrefix` lived only in component state.
- After `groups.insert` creates a new Google Group, Google Workspace doesn't make it queryable by `groupKey` for several seconds. The next call (`members.list`) hit a 404 propagation race and bubbled up as the outer sync error.
- The sync route returned `{ success: true }` only — it never forwarded `added`/`removed`/`failed` from the sync result, so the form's success toast logic always saw zero changes.

**Fix:**
- Form auto-saves via `PUT /api/admin/groups/[id]` before calling `/sync`.
- `syncGoogleGroup` skips `members.list` entirely when it just created the Google Group (an empty new group needs no listing) and wraps subsequent member operations and the settings patch in a `retryOnNotFound` helper that retries up to 4× with 2s backoff on HTTP 404.
- Sync route now passes `added`, `removed`, `failed` arrays through to the client so the toast reflects actual changes.

**Files Modified:**
- `src/components/admin/group-form.tsx` — `formRef` + extracted `buildPayload`/`saveCurrent` helpers; `handleSync` saves pending edits before calling sync
- `src/app/api/admin/groups/[id]/sync/route.ts` — forwards `added`/`removed`/`failed` from sync result
- `src/lib/google-groups.ts` — `isNotFoundError` + `retryOnNotFound` helpers; skip `members.list` on freshly created groups; wrap settings patch and member insert/delete in retry

## 1.11.0 — 2026-05-08

### Feature: Custom RSVP Question + RSVP UX Overhaul

**Value:** Events can now ask attendees one optional question at RSVP/signup time (e.g. "What dish are you bringing?" for potlucks, "T-shirt size?" for service events). The RSVP form on the public event page is also clearer — picking a status no longer instantly saves; users now click an explicit **Submit RSVP** button. Attendee totals across the public and admin views finally include guests, so a 30-spot event with 28 RSVPs and 5 guests correctly reports 33 — and rejects further signups.

#### What's New

**Custom RSVP question (per event, optional)**
- Admin event form has a new "Custom RSVP question" card: type the prompt, choose Free text or Pick-one (dropdown), optionally mark required. Dropdown takes one option per line.
- Question and answer flow through every RSVP/signup surface: authenticated RSVP form, anonymous public RSVP, single-event signup button, and the per-occurrence signup list for recurring events.
- Server validates required answers and (for select type) that the answer is one of the configured options.
- Admin RSVP tables (flat and per-occurrence) get a new column titled with the question label, showing each attendee's answer.

**Clearer RSVP submission**
- Authenticated RSVP form now has explicit submit semantics: Attending / Maybe / Decline buttons select a draft, and a prominent "Submit RSVP" button (or "Update RSVP" when something changed) saves it.
- Saved state is shown via a green "✓ You're attending" indicator next to a disabled "RSVP saved" button.
- New "Remove RSVP" link cancels a saved RSVP without using browser confirms.

**Guests counted in attendee totals**
- Public event page: per-occurrence count and single-event count now sum `1 + guestCount` per non-declined RSVP. Labels read "X attendees (incl. guests)" / "X of Y spots filled (incl. guests)".
- Admin event detail (non-recurring): the green Attending card shows the headcount with a "N members + M guests" subtitle breakdown.
- Admin event detail (recurring): each occurrence's collapsed header shows total headcount with "(incl. guests)" suffix.
- Signup cap check (`/api/events/[id]/signup`) now rejects when `total RSVPs + guests >= maxAttendees`, matching the displayed numbers.

**Form bug fix**
- Admin event form: title input and other text fields no longer flicker between controlled/uncontrolled state. `handleChange` keeps text values as strings instead of coercing `""` to `null`; the API still normalizes empty strings to null on save.

#### Files Added
- `drizzle/migrations/0032_events_extra_question.sql` — adds `extra_question`, `extra_question_type`, `extra_question_options` (jsonb), `extra_question_required` to `events`; adds `extra_answer` to `event_rsvps`

#### Files Modified

- `src/app/api/events/[id]/rsvp/route.ts`, `src/app/api/events/[id]/signup/route.ts` — accept extraAnswer; validate required and select-option answers; signup cap now uses sum-of-guests
- `src/components/public/public-rsvp-form.tsx` — explicit Submit RSVP / Update RSVP button, Remove RSVP link, saved-state indicator, custom question support in both authenticated and anonymous modes
- `src/components/events/single-event-signup.tsx` — custom question above the Sign Up button; "incl. guests" label
