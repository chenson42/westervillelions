## 1.13.0 — 2026-05-18

### Feature: Cancel a Single Event Occurrence

**Value:** Recurring events sometimes skip an individual date — e.g., the farmers market runs May–September but doesn't happen on July 4. Previously there was no way to represent this; the date would still appear in the signup list as though it were active. Admins can now cancel a single occurrence, attach an optional reason, and reverse the cancellation at any time. Members see the cancelled date with a badge and reason rather than a signup button; members who had already signed up see a "You were signed up for this date" note.

#### What's New

- **Admin cancel/restore.** On the event detail page (`/admin/events/[id]`), each occurrence row in the "Signups by Occurrence" accordion now has a "Cancel" button. A modal dialog collects an optional reason. The button becomes "Restore" once cancelled; restore is confirmed via a simple confirm dialog. Both actions update the row immediately without a page reload.
- **Cancelled badge on public and member-portal pages.** On `/events/[id]` and `/members/events`, cancelled occurrence rows show an amber "Cancelled" badge in place of the signup button. The cancellation reason (if provided) appears in subdued italic text beneath the date.
- **"You were signed up" note.** Members who had an existing RSVP for a now-cancelled occurrence see an amber notice — "You were signed up for this date." — alongside the badge. Their RSVP record is preserved in the database; admins can still see who had signed up in the admin accordion.
- **Next-occurrence skips cancelled dates.** The `/events` public list, `/members/events` portal list, `/members/events/past`, admin `/admin/events` list, and the homepage all skip cancelled dates when computing the "next occurrence" for a recurring series. The series still appears in the list pointing to the next uncancelled date.
- **Signup guard.** The `POST /api/events/[id]/signup` route now rejects signups for cancelled occurrences with a `400` response, even if a client somehow submits one.
- **Orphaned cancellation records.** If an admin edits the recurrence rule so that a previously cancelled date falls outside the new generated window, the admin accordion surfaces it as an extra row labelled "outside current recurrence rule." Admins can Restore (delete) the record to clean up.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `events.edit` | Cancel and restore an occurrence via the new API endpoint. Same roles that already hold this key — no new binding needed. |

#### New Routes

- `POST /api/admin/events/[id]/occurrences/[date]/cancel` — Toggle cancellation state. Body: `{ cancelled: boolean, reason?: string }`. `[date]` is a `YYYY-MM-DD` string. Guarded by `auth()` + `FEATURES.EVENTS_EDIT`. Cancel upserts a row in `event_occurrence_overrides`; restore deletes it.

#### Schema Changes

- **New table `event_occurrence_overrides`** — one row per cancelled occurrence. Columns: `id` (UUID PK), `event_id` (FK → `events`, cascade delete), `occurrence_date` (plain `DATE`, no time component — architecturally locked per DECISION-001), `cancelled_at` (TIMESTAMPTZ), `cancelled_by_user_id` (FK → `users`, set null on delete), `cancellation_reason` (nullable text). Composite unique on `(event_id, occurrence_date)`.
- **Migration:** `drizzle/migrations/0036_event_occurrence_overrides.sql` (fully idempotent — `CREATE TABLE IF NOT EXISTS` + guarded `DO $$ … END $$` for the unique constraint).
