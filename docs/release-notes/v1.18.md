## 1.18.3 — 2026-05-27

### Security: First-Login Guard on Unlinked-User Notification; Feature Gate on Email-Queue Retry

**Background:** Two medium-severity findings from the 2026-05-27 security review.

- **F6:** The "unlinked user signed in" admin notification fired on *every* sign-in by any user without a `memberId` — not just the first one. A user stuck in unlinked state could flood `info@westervillelions.org` with notification emails by signing in repeatedly. The three fire-and-forget DB operations in the JWT callback (lastLoginAt update, auto-link, notify) also raced each other.
- **F5:** `/api/admin/email-queue/retry` checked `session.user.roles?.includes("admin")` instead of `hasFeature()` — the only route in the codebase using that pattern, inconsistent and using stale session data.

**Changes:**
- Restructured the JWT callback: the three DB operations now run sequentially inside a single async block. The unlinked-user notification fires only when `lastLoginAt` was `NULL` at sign-in time (true first-ever login) **and** auto-link didn't resolve the membership. The user's name and email are now HTML-escaped before going into the email body.
- `/api/admin/email-queue/retry` and `/admin/email-queue` page now require `FEATURES.ADMIN_USERS` via `hasFeature()` — consistent with all other admin surfaces. No migration needed; the Admin role already holds this feature.

## 1.18.2 — 2026-05-27

### Security: Export Endpoints Require REPORTS_EXPORT; CVE Patches for Next.js and drizzle-orm

**Background:** The 30-day code and security reviews independently flagged that `/api/admin/members/export` and `/api/admin/newsletter/export` checked only `auth()` — any logged-in member could download the full active-member roster (name, email, phone, address) or the full newsletter subscriber list. Separately, the dependencies and security reviews flagged that `next` 16.1.6 carried 8 high CVEs (middleware/proxy bypass, SSRF via WebSockets, Server Components DoS) and `drizzle-orm` 0.45.1 carried a SQL-injection CVE via improperly escaped identifiers. All of these are patched upstream.

**Changes:**
- Both export endpoints now require `FEATURES.REPORTS_EXPORT` in addition to a valid session. Members without that feature receive `403 Forbidden`. The Admin role already holds this feature; no migration needed.
- Bumped `next` 16.1.6 → 16.2.6 and `eslint-config-next` 16.1.1 → 16.2.6 (closes 8 high CVEs).
- Bumped `drizzle-orm` 0.45.1 → 0.45.2 (closes the identifier-escape SQLi).
- Corrected the 2026-05-27 code review's MEDIUM-2 finding: `src/proxy.ts` is the Next.js 16 middleware convention (renamed from `middleware.ts`), not dead code. The build output confirms it is registered as `ƒ Proxy (Middleware)`.

## 1.18.1 — 2026-05-27

### Defect Fix: Admin Events List Attending Count Excluded Guests

**Problem:** On `/admin/events`, the expanded RSVP summary for each event ("✓ N attending · ~ N maybe · ✕ N declined · N total") only counted RSVP rows, not the people each RSVP represented. An RSVP marked "attending" with 2 guests counted as 1, not 3 — so the headline number on the list page understated turnout for any event where guests were allowed and used.

**Root Cause:** The per-event rollup query grouped by status and used `count(*)`, ignoring the `guest_count` column entirely. Other surfaces (the per-event detail page, the public signup endpoint) already counted each RSVP as `1 + guestCount` people; the list view had silently drifted out of sync.

**Fix:** The list page's rollup now sums `guest_count` alongside the row count and adds both into the attending / maybe / declined / total buckets — matching the convention already used on the event detail page (`attending.length + totalGuests`) and the public signup endpoint.

**Testing:**
- [x] Typecheck and production build both pass
- [x] Existing unit tests (115) pass — no test setup creates RSVPs with non-zero `guest_count`, so the change is functionally a no-op for the existing e2e regression suite on `recurring-signup-rollup.spec.ts`

## 1.18.0 — 2026-05-22

### Feature: Plastic-Film Drop-Off Locations

**Value:** The plastic-film recycling card on `/programs` was a hardcoded reference to a single Pure Roots location. Adding a second host (or correcting a phone number, or updating an entry-instructions line) required a code deploy. The eyeglass drop-off card has always been admin-managed; bringing plastic up to the same model lets the club expand the program without engineering involvement.

#### What's New

- **Admin manager** at `/admin/programs` — a new "Plastic Drop-Off Locations" section directly below the eyeglass section. Same controls: add, edit, toggle active/inactive, delete (with `<ConfirmDialog>`), reorder by sort key.
- **Two extra fields** beyond the eyeglass schema:
  - **Entry instructions** — short free text, e.g. "Enter through the back door." Shows under the address on the public card.
  - **Hours** — short free text, e.g. "Saturdays during the summer."
- **Dynamic public render.** The `/programs` plastic card body now lists every active plastic drop-off location pulled from the database, with the same visual treatment as the glasses card.
- **Empty state.** If no plastic sites are active, the card shows "Locations coming soon — check back shortly or contact us for details." rather than going blank.
- **Two seed sites included.** A first deploy populates the table with Pure Roots Boutique (Westerville, OH; "Enter through the back door.") and the Westerville Farmers Market (COhatch parking lot, 240 S. State St; "Come find us at the Westerville Lions tent."; "Saturdays during the summer"). Both can be edited or removed from the admin UI.

### Enhancement: Drop-Off Location Layout + Google Maps Links

**Value:** On the previous build, the drop-off location block was pinned to the bottom of each program card via `mt-auto`, which left a large empty gap when one card's location list was much shorter than the other's. And neither card surfaced a way to actually navigate to the listed address — visitors had to copy the text into their own maps app.

**Changes:**

- The "Drop-off Locations" block now sits immediately under the intro paragraph on **both** the eyeglass and plastic cards — above "What we accept / cannot accept." The actionable information (where to drop off) leads; the educational lists trail.
- Every drop-off row on **both** cards now shows a small map-pin icon next to the address. Tapping it opens a Google Maps search for that address in a new tab. The link is auto-derived from the existing `address` field — no schema change, no admin work, applies to every existing eyeglass site for free.

#### Permissions

| Feature key | Required for |
|-------------|--------------|
| `announcements.manage` (existing) | Adding, editing, toggling, or deleting plastic drop-off locations. Same key the eyeglass admin uses. No new permission. |

#### New Routes

- `GET /api/admin/programs/plastic-dropoff` — list all plastic drop-off locations (admin only).
- `POST /api/admin/programs/plastic-dropoff` — create a new location.
- `PATCH /api/admin/programs/plastic-dropoff/[id]` — partial update.
- `DELETE /api/admin/programs/plastic-dropoff/[id]` — hard delete.

#### Schema Change

A new table `plastic_dropoff_locations` was added (`name`, `address`, `phone`, `entry_instructions`, `hours`, `is_active`, `sort_order`, timestamps). Migration `0039_plastic_dropoff_locations.sql` is idempotent: `CREATE TABLE IF NOT EXISTS`, and each seed `INSERT` is guarded by `WHERE NOT EXISTS (SELECT 1 ... WHERE name = ...)` so admins can rename or delete seed rows without the migration silently restoring them on the next deploy.
