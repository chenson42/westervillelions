# Technical Design: Event Signups with Per-Occurrence Support

**Date:** 2026-04-29
**Status:** Ready for implementation
**Agents:** database-admin, api-developer, ux-developer

---

## Summary

We are extending the existing RSVP system to support per-occurrence signups on recurring events. Today, `event_rsvps` tracks a single response per user per event with no awareness of which date they signed up for. This design adds an `occurrence_date` column to `event_rsvps`, a new `POST/DELETE /api/events/[id]/signup` route pair (login-required, simpler model than the existing anonymous-capable `/rsvp` route), a utility to generate all occurrence dates for a recurring series, and UI components to render per-occurrence signup rows on both the public event detail page and the admin event detail page.

The existing `/api/events/[id]/rsvp` route and `PublicRsvpForm` component are **not changed** — they continue handling the status-based (attending/maybe/declined) RSVP flow for non-recurring events. The new signup route is a separate, simpler interaction: sign up or cancel, no status nuance.

---

## 1. Schema Changes

### 1a. New column on `event_rsvps`

```sql
ALTER TABLE event_rsvps ADD COLUMN IF NOT EXISTS occurrence_date TIMESTAMP;
```

- NULL = non-recurring event signup (existing rows unaffected)
- Non-null = the exact start timestamp of the occurrence (must match a value generated by the recurrence engine)

### 1b. Unique constraint strategy

PostgreSQL treats every NULL as distinct, so `UNIQUE(event_id, user_id, occurrence_date)` would allow unlimited duplicate rows when `occurrence_date IS NULL`. We solve this with **two partial unique indexes** — one for each case — instead of a single table constraint.

```sql
-- One signup per user per occurrence (recurring)
CREATE UNIQUE INDEX IF NOT EXISTS uq_event_rsvps_recurring
  ON event_rsvps (event_id, user_id, occurrence_date)
  WHERE occurrence_date IS NOT NULL AND user_id IS NOT NULL;

-- One signup per user for non-recurring event (NULL occurrence_date)
CREATE UNIQUE INDEX IF NOT EXISTS uq_event_rsvps_non_recurring
  ON event_rsvps (event_id, user_id)
  WHERE occurrence_date IS NULL AND user_id IS NOT NULL;
```

Notes:
- Anonymous rows (`user_id IS NULL`) are excluded from both indexes. The anonymous RSVP flow already deduplicates by `rsvp_email`; we leave that behavior alone.
- The indexes are partial so they do not conflict with existing rows that have `occurrence_date IS NULL`.
- Both indexes are idempotent via `IF NOT EXISTS`.

### 1c. Drizzle schema update (`src/lib/db/schema.ts`)

Add to `eventRsvps`:

```typescript
occurrenceDate: timestamp("occurrence_date"),
```

No change to any other table.

## 2. Occurrence Generation Utility

### Existing utility assessment

`src/lib/events.ts` has `getNextOccurrence()` (returns a single next date) and `formatRecurrence()` (returns a label string). Neither generates a full list of dates.

### New function: `generateOccurrences`

Add to `src/lib/events.ts`:

```typescript
/**
 * Generates all occurrence dates for a recurring event, ordered ascending.
 * For non-recurring events returns [event.startDate].
 *
 * @param event   Event fields needed to compute recurrence
 * @param from    Start of window (default: now). Occurrences before this are excluded.
 * @param maxWeeks  Maximum weeks to generate into the future (default: 52).
 *                  Ignored if recurrenceEndDate is set and is sooner.
 */
export function generateOccurrences(
  event: RecurringEvent,
  from: Date = new Date(),
  maxWeeks = 52
): Date[] {
  // ...
}
```

**Algorithm:**

1. If `!event.isRecurring`, return `[event.startDate]` (single occurrence).
2. Set `windowEnd = min(recurrenceEndDate ?? Infinity, addWeeks(from, maxWeeks))`.
3. Walk forward from `max(event.startDate, from)` to `windowEnd`, advancing by the recurrence interval (1 day at a time for weekly/biweekly to check day-of-week, 1 month for monthly), collecting matching dates. Reuse the biweekly `weeksDiff % 2` logic already in `findNextDayOfWeek`.
4. For **monthly**: same day-of-month as `event.startDate`, advance one month per step.
5. For **weekly/biweekly**: iterate days, check `recurrenceDays.includes(candidate.getDay())`, and for biweekly check `(weeksDiff % 2 === 0)`.
6. Each occurrence inherits the time portion from `event.startDate`.
7. Cap at 200 occurrences to guard against misconfigured open-ended series.

**Lookback window for past occurrences (admin view):** The admin detail page needs past occurrences too. It calls `generateOccurrences(event, event.startDate)` — i.e., no `from` filter — so all occurrences from series start are returned. The UI then partitions them into past vs. upcoming.

**No end date:** If `recurrenceEndDate` is null, `maxWeeks = 52` caps the forward window. For the admin full-history view, use `maxWeeks = 520` (10 years) as a safety cap — practically these series always have an end date.

## 3. API Design

### Why a new route instead of extending `/rsvp`

The existing `/api/events/[id]/rsvp` route supports anonymous users (name + email), three statuses, and guest counts. That complexity is correct for the legacy RSVP model. The signup feature is login-required and binary (signed up or not). Merging them would require an `occurrenceDate` parameter in the existing route and conditional logic throughout. A separate route is cleaner.

### `POST /api/events/[id]/signup`

**File:** `src/app/api/events/[id]/signup/route.ts`

**Auth:** Login required. Return `401` if no session.

**Request body:**
```typescript
{
  occurrenceDate?: string; // ISO 8601 timestamp, required for recurring events
}
```

**Validation:**
1. Event exists — else `404`.
2. `event.requiresRsvp === true` — else `400 { error: "Signups are not enabled for this event" }`.
3. If `event.isRecurring`: `occurrenceDate` is required — else `400`. Parse to `Date`. Verify it is a valid occurrence by calling `generateOccurrences(event, event.startDate)` and checking membership (match to minute precision). If invalid: `400 { error: "Invalid occurrence date" }`.
4. If `event.isRecurring` and `occurrenceDate` is in the past: `400 { error: "Cannot sign up for a past occurrence" }`.
5. Check cap: count existing `event_rsvps` rows where `eventId = id` AND `occurrenceDate = <parsed>` (or `occurrenceDate IS NULL` for non-recurring) AND `status != 'declined'`. If `event.maxAttendees` is set and count >= cap: `409 { error: "This occurrence is full" }`.
6. Upsert by `(event_id, user_id, occurrence_date)`: if row exists and `status = 'attending'`, treat as no-op (return existing). Otherwise insert with `status = 'attending'`.

**Response `201`:**
```typescript
{
  id: string;
  eventId: string;
  userId: string;
  occurrenceDate: string | null; // ISO
  status: "attending";
  createdAt: string;
}
```

**Response `200`** (already signed up — idempotent):
```typescript
{ alreadySignedUp: true }
```

### `DELETE /api/events/[id]/signup`

**File:** Same file, `export async function DELETE`.

**Auth:** Login required. Return `401` if no session.

**Request body:**
```typescript
{
  occurrenceDate?: string; // required for recurring events
}
```

**Logic:**
1. Event exists — else `404`.
2. For recurring: parse and validate `occurrenceDate` is present.
3. Delete `event_rsvps` row where `event_id = id AND user_id = session.user.id AND occurrence_date = <parsed>` (or IS NULL for non-recurring).
4. If no row found: return `200 { success: true }` anyway (idempotent).

**Response `200`:**
```typescript
{ success: true }
```

### Attendance count query (used by both public page and admin)

To load signup counts per occurrence efficiently (no N+1), the server fetches all RSVPs for an event in one query and groups them in TypeScript:

```typescript
const allRsvps = await db
  .select({
    occurrenceDate: eventRsvps.occurrenceDate,
    userId: eventRsvps.userId,
    userName: users.name,
    userEmail: users.email,
    status: eventRsvps.status,
  })
  .from(eventRsvps)
  .leftJoin(users, eq(eventRsvps.userId, users.id))
  .where(
    and(
      eq(eventRsvps.eventId, eventId),
      eq(eventRsvps.status, "attending")
    )
  );
```

Group by `occurrenceDate.toISOString()` in memory to build a `Map<string, SignupRow[]>`.

## 4. `requiresRsvp` Column Usage

**Decision: reuse `requiresRsvp` as-is.** Do not rename it, do not add an `allowSignups` column. The admin form already shows "Requires RSVP" — update the label to "Allow Signups / RSVP" in `event-form.tsx` to reflect the broader meaning. This avoids a schema migration and a backfill.

The label change in the form is the only admin form modification needed for this feature. The `maxAttendees` field already exists and already appears in the form.

## 5. UI Component Breakdown

### 5a. New utility (shared)

**`src/lib/events.ts`** — add `generateOccurrences()` as described in section 2. No new file needed.

### 5b. New component: `OccurrenceSignupList`

**File:** `src/components/events/occurrence-signup-list.tsx`

A client component. Renders the list of upcoming occurrences for a recurring event, each with a signup/cancel button. Props:

```typescript
interface OccurrenceSignupListProps {
  eventId: string;
  occurrences: OccurrenceRow[];        // generated server-side, passed as props
  maxAttendees: number | null;
  isLoggedIn: boolean;
}

interface OccurrenceRow {
  date: string;           // ISO timestamp (occurrence start)
  displayDate: string;    // pre-formatted: "Mon, May 5 at 6:00 PM"
  signedUpCount: number;  // from DB
  isSignedUp: boolean;    // current user's status
  isFull: boolean;        // signedUpCount >= maxAttendees (false if no cap)
  isPast: boolean;
}
```

**Button state machine per row:**

| State | Button label | Button appearance |
|-------|-------------|------------------|
| `isPast` | Closed | Gray, disabled |
| `isFull && !isSignedUp` | Full | Gray, disabled |
| `isSignedUp` (loading) | ... | Blue, disabled |
| `isSignedUp` | Signed Up | Blue filled, clickable (cancel on click) |
| default (loading) | ... | Outline, disabled |
| default | Sign Up | Blue outline, clickable |

**Interaction:** clicking Sign Up calls `POST /api/events/[id]/signup` with `{ occurrenceDate }`. Clicking Signed Up calls `DELETE /api/events/[id]/signup`. Optimistic update: flip `isSignedUp` and adjust `signedUpCount` immediately; revert on API error. Show toast on success/error.

**Login gate:** If `!isLoggedIn`, all buttons are replaced with a single `"Log in to sign up"` link (href="/signin").

### 5c. New component: `SingleEventSignup`

**File:** `src/components/events/single-event-signup.tsx`

A simpler client component for non-recurring events. Props:

```typescript
interface SingleEventSignupProps {
  eventId: string;
  signedUpCount: number;
  maxAttendees: number | null;
  isSignedUp: boolean;
  isLoggedIn: boolean;
}
```

Renders a single Sign Up / Signed Up / Full button with a count display ("3 of 10 signed up" or "3 signed up" if no cap). Same button state machine as above, without the row structure.

### 5d. Modified: public event detail page

**File:** `src/app/events/[id]/page.tsx`

**Server-side data additions:**
- Call `generateOccurrences(event, new Date())` to get upcoming dates (next 52 weeks).
- Query `event_rsvps` for this event with `status = 'attending'` — one query, group by `occurrenceDate` in TypeScript.
- For logged-in users: query their specific RSVPs for this event to determine `isSignedUp` per occurrence.

**Render logic:**
```
if event.requiresRsvp:
  if event.isRecurring:
    render <OccurrenceSignupList>
  else:
    render <SingleEventSignup>
    render <PublicRsvpForm>  ← keep existing for status/guest-count functionality
```

For non-recurring events, `SingleEventSignup` and `PublicRsvpForm` coexist: `SingleEventSignup` handles the binary signed-up state, `PublicRsvpForm` continues to handle the attending/maybe/declined status. The two use the same underlying `event_rsvps` row (occurrence_date = NULL). On signup via `SingleEventSignup`, the row is created with `status = 'attending'`; `PublicRsvpForm` reads and updates that status. This may cause a slight UX redundancy — see Edge Cases section 7 below.

**Alternative (simpler):** For non-recurring events, replace `PublicRsvpForm` with `SingleEventSignup` only, and drop the attending/maybe/declined distinction for the signup feature. Recommend revisiting this decision before implementation starts — the two forms operating on the same row create potential confusion. If the status model is kept, `SingleEventSignup` should check `status !== 'declined'` when computing `isSignedUp`.

### 5e. Modified: admin event detail page

**File:** `src/app/(dashboard)/admin/events/[id]/page.tsx`

**For recurring events:** Replace the flat RSVP table with a grouped view. Server-side:
- Call `generateOccurrences(event, event.startDate)` to get all occurrences (past + future).
- Query all RSVPs for the event (one query, join users).
- Group rows by `occurrenceDate.toISOString()`.

Render an expandable section per occurrence (past occurrences collapsed by default, similar to the existing expandable RSVP summary rows on the admin events list). Each occurrence section shows:
- Date/time header
- Signed-up count (and cap if set)
- Table of signees: name, email, signed-up timestamp

**For non-recurring events:** existing flat table is unchanged.

**Reuse pattern:** The admin events list (`src/app/(dashboard)/admin/events/page.tsx`) already has expandable rows. The same disclosure/accordion pattern should be used here.

### 5f. Modified: admin event form

**File:** `src/components/admin/event-form.tsx`

Single label change only:
- `"Requires RSVP"` → `"Allow Signups / RSVP"`
- Update the helper text: `"Members can sign up for this event. For recurring events, signups are per occurrence."`

No logic changes.

## 7. Edge Cases and Risk Decisions

### Race condition on full events

When two members click Sign Up simultaneously for the last slot, both requests pass the cap check and both attempt insert. The partial unique index prevents duplicate rows (one insert will fail with a unique violation). The API should catch this postgres error (code `23505`) and return `409 { error: "This occurrence is full" }`. The UI should handle `409` by flipping the button to "Full" and showing a toast.

### Canceling a past occurrence

`DELETE /api/events/[id]/signup` with a past `occurrenceDate`: we allow it. There is no harm in letting a member undo a signup for a past occurrence (it adjusts historical count). The public UI hides past occurrence rows so members won't encounter this normally, but the API does not block it.

### Recurring event with no end date

`generateOccurrences` caps at `maxWeeks = 52` (forward) on the public page. Admin full-history view uses `from = event.startDate` with `maxWeeks = 520`. Both paths also cap at 200 occurrences total. This is sufficient for any realistically configured club event.

### Occurrence date validation

The API must validate that the submitted `occurrenceDate` is a real occurrence of the series, not an arbitrary timestamp. Validation: generate the full occurrence list server-side (same `generateOccurrences` call), then check that the submitted date matches any entry within ±1 minute (to handle minor client/server clock drift or timezone serialization). Match on UTC milliseconds after rounding to the minute.

```typescript
function isValidOccurrence(candidate: Date, occurrences: Date[]): boolean {
  const t = Math.round(candidate.getTime() / 60000);
  return occurrences.some((o) => Math.round(o.getTime() / 60000) === t);
}
```

### Non-recurring event: coexistence of `/signup` and `/rsvp` routes

Both routes operate on the same `event_rsvps` table with `occurrence_date IS NULL`. The signup route upserts with `status = 'attending'`; the RSVP route may later update that status to 'maybe' or 'declined'. This is intentional: signing up creates the row, and the RSVP status can be refined separately. The `isSignedUp` display on `SingleEventSignup` should check `status IN ('attending', 'maybe')` — effectively "not declined" — so the button stays highlighted even when status is 'maybe'.

**Recommendation:** Strongly consider deprecating the attending/maybe/declined model for events that use the new signup system and just use the binary sign-up. This would be a cleaner UX. Out of scope for this feature but worth tracking.

### Timezone handling

All timestamps in the DB are stored without timezone (`TIMESTAMP` not `TIMESTAMPTZ`). The existing codebase uses this convention consistently. Occurrence dates generated by `generateOccurrences` inherit the time from `event.startDate` (local time as stored). When the client submits `occurrenceDate`, it must send the same local ISO string that was rendered to the user, not a UTC-converted version. The API validates against generated occurrences using the same timezone-unaware comparison.

### Members who sign up then the cap is lowered

If an admin lowers `maxAttendees` after signups exist, existing rows are not removed. The cap applies only to new signups. Current attendees remain signed up. This is the correct behavior.
